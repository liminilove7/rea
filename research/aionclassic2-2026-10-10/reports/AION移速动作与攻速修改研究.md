# AION 移速 动作与攻击速度修改研究

移速、动画播放速度和攻击请求计时分别由不同字段控制。最有价值的研究入口是 CharacterObject 家族的速度设置函数 `460440`、动画比例函数 `4BC390` 和本地攻击请求函数 `06A0B0`；只改面板缓存、武器说明或技能冷却，不能据此判断角色真实移动或攻击是否加快。

以下针对 Game.dll SHA-256 `834300c2a85b6427de2d4a4be2931ff2ea59fd70f48f31754f5c2181753bd786`。函数地址是 RVA，运行时地址为对应 Game.dll 模块基址加 RVA；对象字段须加到已确认的运行时对象指针上。静态基址 `180000000`、属性编号和对象偏移不能互换。

## 先选对修改对象

| 研究目标 | 具体位置和类型 | 已确认用途 | 用于判断修改效果 |
| --- | --- | --- | --- |
| 客户端移动速度 | CharacterObject家族对象 `+6C8`，float32 | 被速度设置函数写入，移动动画和向量限制路径读取 | 同时观察位移、动画及关联派生值；不能只看面板 |
| 同一速度的派生表示 | 同对象 `+6CC` 为速度平方，`+6D0` 为倒数，都是float32 | 位置差异比较和方向插值使用不同派生表示 | 单独写 `+6C8` 会留下不一致的平方和倒数，可能出现不同消费者表现不一致 |
| 本地速度缓存 | `Game.dll+D71CA0`，float32 | 仅本地对象身份匹配时由设置函数更新 | 它是缓存；尚无证据表明只改它就改变世界位移 |
| 攻击动画比例 | 同家族对象 `+508/+50A`，uint16；`+4F4`，float32 | `cattack` 分支使用两项间隔之比，再乘全局动画比例 | 分别量动画周期、请求产生间隔和伤害发生间隔 |
| 本地攻击时间门槛 | 对象 `+1C88`，uint32；全局 `Game.dll+D71BE0`，uint16 | `06A0B0` 用它们与保护时钟返回值比较 | 它比动画倍率更接近请求调度；仍有其他条件和服务端接受环节 |
| 时间基准调整状态 | 同对象 `+1C94`，float32；`+1C98`，uint32 | `05D140` 补充额度并可能重写 `+1C88` | 改动后立即恢复或表现漂移时，应追这些写入者 |
| 物理层运动向量 | CryPhysics的CLivingEntity对象 `+178/+17C/+180`，三个float32 | 已选运动请求分支把三项输入写入此处 | 与Game组件速度标量分开识别；当前已验证局部原指令写入，尚未做完整物理积分或游戏修改 |
| 动作状态 | 同家族对象 `+AB0/+AB4`；技能动作另有 `+14A8/+14AC` | 在不同动作处理路径中控制分支 | 不能把这些偏移合并为一个统一动作编号，也不能先给未知枚举命名 |

Player、AIObject等类共享部分速度接口；实体对象、组件对象和物品记录也有同偏移字段。识别对象须核对构造、虚表或调用传入的 `this`，不能靠扫描出相同数字确认。

## 移速要追设置链和覆盖来源

`460440` 接受 float32 速度 `s`，在正常有限输入下维护以下关系：

```text
object+38  = s
object+6C8 = s
object+6CC = float32(s*s)
object+6D0 = float32(1/s)  // 接近零时走特殊分支，写1
```

它还更新动画和状态。本地玩家匹配时再写全局缓存 `D71CA0`。因此研究时先在这个设置入口观察原来输入、对象身份和调用来源，记录下一次谁重新设置速度，比直接冻结面板缓存更能解释修改为什么恢复。

历史消息路径是 `430410→4EB620→组件虚表+248→460440`。最新已核对的 Player 原始虚表同一槽仍指向 `460440`。另有 `4BF3C0` 根据关联对象派生速度，再调用相同设置接口；其分支中出现的12和30不是已经证明的全角色速度上限。

不同速度消费者的作用也不同：`4677C0` 使用 `s²` 比较位置差异；`4C30CA→0B4B80` 使用倒数形成方向样式向量插值；`4BBA10` 有 `min(s,L)/L` 的平面向量缩放。方向变化、位置差异容差与坐标积分应分开研究。后续已用归档的CryEntitySystem和CryPhysics补证选定实体/物理接口，见下文；完整物理积分和实时对象类型仍须继续查证。

这里的实体指针来自组件 `this+8`：`4BBA10` 在取虚槽 `+178` 前重新加载它，`4BE930` 的末端提交也使用关联实体。不能拿 Player 自身虚表同一槽的地址当成这些调用目标；偏移数字相同，接收对象仍不同。

验证一个速度改动时，记录静止、正常行走、停止、转向和收到状态更新前后的对象字段，并分别测量本地坐标变化与服务器后续确认的位置。如果面板改变而坐标变化不变，应继续追执行消费者；如果短时改变后恢复，应追覆盖入口。以上是待执行的验证方法，当前未产生运行时修改结果。

## 攻击动画与请求间隔分开量

`4BC390` 的 `cattack` 分支令 `B=u16(object+508)`、`C=u16(object+50A)`、`G=float32(object+4F4)`，正常非零输入时：

```text
R = float32(float32(B/C)*G)
```

任一间隔为零时，这一分支回退到1后再乘G。例如 `B=2000、C=1000、G=1` 得到动画倍率2。这个算例说明画面播放比例，不是已经验证的两倍有效攻击频率。

同版 Game 的[收到动作处理指令](../evidence/continuous/20261013-movement-action-speed/received-action-speed-sync.normalized.json) `430410` 在内部动作编号35的分支，将载荷 `+B/+D` 两个uint16写入组件 `+508/+50A`（指令 `430710/430717`）。因此即使某个绿色全局攻速缓存变化，**动画这一侧还取决于当前组件的收到动作字段**；下一次收到动作也可能重写它们。旧版服务端消息结构与基础/当前攻击间隔相符，但当前版本编号的完整业务含义和两值单位仍按未知保留。

动画比例也不是完全脱离攻击请求的显示数字：已定位 `47C940→47CC70→06A0B0`，动画事件参数会除以比例R，再参与构造请求缓冲区 `+C` 的uint16参数。但是同一攻击函数另有时间门槛，而且内部缓冲区尚未建立当前线路抓包与服务器接受绑定。

所以应同时记录三个量：完整攻击动画持续时间、本地请求构造次数和服务器返回的实际伤害事件。只看到角色挥得更快、只看到内部缓冲区字段变小，均不足以判断有效攻击次数增加。

## Game 到 CryAnimation 的实际倍率写入

这版归档的 CryAnimation.dll SHA-256 为 `32f492dc373e22aa43647546b888e0420044b84a7039a40dc99f6e91b5a637ac`。先前 Game 内只找到动画比例的计算；现在又沿原始 CryEntitySystem 与 CryAnimation RTTI 虚表，把**能够进入 `cattack` 比例分支的动作播放路径**追到引擎写入处：

```text
Game CharacterObject 动作处理 493940
  → 493A85: 组件+8 的 CEntity 主虚表+580
  → CryEntitySystem CEntity::17300: 返回 Entity+E8 子接口
  → 493A93: 该子接口虚表+20
  → CryEntitySystem 23DE0: 参数0时取得 Entity+300 保存的角色动画对象指针
  → 4941BA: Game 4BC390 计算当前动作的动画倍率R
  → 494611: 角色动画对象虚表+360，传入R及动作层编号
  → CryAnimation CryCharInstance::54E10: 写实例+328，然后转入 B0AD0 更新该层倍率表
```

这条绑定由 CEntity 主虚表、其 `+E8` 子对象虚表和 CryCharInstance 主虚表中的原始指针核对。`Game 460440` 的移动速度设置入口也经 Entity `+580`/子接口 `+20` 调用动画对象 `+360`，分别设置两层倍率。说明 Game 中既有速度标量/比例计算，也通过引擎动画对象保存播放倍率；`Game.dll+D71CA0` 等全局缓存不是 CryAnimation 对象中的最终播放槽。

CryAnimation `54E10` 首先把输入 float32 写入实例 `+328`；`B0AD0` 仅在层号0..16、倍率非负且小于1000000时把同一值写入该层倍率表。五组软件 CPU 原指令实验中，层0输入2时两个槽都变成2；输入负数、1000000或层17时实例槽先改变，层倍率表仍为旧值1，并进入错误日志分支。这是一个实际的“内存读回已经改变，但动画层没有接受”的反例。边界值只是该接口参数校验，**不是游戏允许的有效攻速范围**。

上述原始虚表、REA 指令窗口、[离线实验](../evidence/continuous/20261013-animation-interface/offline-animation-setter-experiments.json)和[身份/字节核对](../evidence/continuous/animation-interface-verification.json)可复查。虚调用的实际接收者、动作层号以及角色画面速度没有运行时采样，所以不能把 CryCharInstance 的对象 `+328` 当成已取得的在线角色地址。动画倍率即使由该接口接受，普通攻击仍须经过 `061C20→042860→06A0B0` 的本地调度和服务端实际结算。

## 本地时间门槛及动作覆盖

`06A0B0` 在已读分支先调用 `05D140(object, XMM1=0)`，再读取保护入口 `1244AE3` 返回值的低32位 `n`：

```text
threshold = u32(object[+1C88] + u16(Game.dll+D71BE0))
n <= threshold 时拒绝这个分支
通过后继续检查和构造请求；成功路径更新 object[+1C88] = n
```

`05D140` 还维护 `+1C94/+1C98`：时间差大于5000时按整段补充额度，每段约0.2，最高0.5。在适用动作和调整条件下，它又会重写 `+1C88`。这解释了为什么单次改变某个时间值，不能等同于稳定控制调度周期。5000、1000与时间换算相容，但这里保护时钟的运行时来源和单位尚未采集，不能把额度0.5直接命名为半秒前摇。

动作 `+AB4` 的1031/1028/1027/1029分支读取动作记录 `+920/+924`，计算调整量。当前只是具体枚举值和数据来源，完整业务名称尚未恢复。技能施放的 `+14A8/+14AC` 属于另一条动作路径；应该从一次明确操作的写入者反推动作语义，避免直接按偏移猜“取消后摇”。

当前重新取得的 Player 更新 `061C20` 从 `+14A8` 分派：动作1调用 `042860`，动作2调用 `046ED0`，动作9和10在各自条件满足时也调用 `042860`。`042860` 内部读取 `+14AC`，通过目标/方向相关条件后在 `042FF1` 调用 `06A0B0`。因此普通攻击动作研究应沿 `061C20→042860→06A0B0` 观察；动作编号9/10的完整业务名称仍未确认，不能统一命名成普通攻击或技能。

## 原始指令离线修改实验

已在软件CPU中执行同哈希 Game.dll 的三个原始片段，使用明确构造的对象、寄存器和时钟值，没有启动游戏。以下结果说明局部代码怎样响应改动，不能当成服务器接受结果。

| 实验 | 实际片段结果 | 对修改研究的意义 |
| --- | --- | --- |
| 完整速度设置前缀，输入6 | `+6C8=6、+6CC=36、+6D0≈0.166667` | 确认三个速度表示同步形成 |
| 完整速度设置前缀，输入9 | `+6C8=9、+6CC=81、+6D0≈0.111111` | 速度提高时平方和倒数也改变；直接写单字段不具备这一效果 |
| 速度设置前缀，输入0 | 平方为0、倒数槽为1 | 近零特殊分支不是通常的除零倒数 |
| cattack间隔2000/1000，全局比例1 | 动画倍率2 | 得到播放倍率，尚未通过后面的攻击调度 |
| 相同间隔，全局比例2 | 动画倍率4 | 全局比例也参与结果，不能只改一对间隔来归因 |
| 时间基准1000、间隔200，时钟1200 | 本地比较拒绝 | 等于截止值仍不通过 |
| 相同基准和间隔，时钟1201 | 本地比较通过 | 明确的无符号“大于”边界；后续其他检查仍在 |

设置前缀停在实体回调之前；动画实验直接进入已经选择好的cattack片段；时间实验不调用保护时钟或额度调整函数。所有输入、原指令字节、执行步数和停点都保存在[实验结果](../evidence/continuous/20261013-movement-action-speed/offline-original-field-experiments.json)。另有单字段改动的数据对照和uint32回绕例子，分别标明来源，未混作运行时实测。

[实验脚本](../client/analysis-code/continuous/emulate-movement-attack-fields.py)可重跑，`--speed`可重复传入速度值，`--output`必须指定尚不存在的输出文件。复现使用本机独立 `AION_Offline` Python环境中的Unicorn与Capstone；输出不会修改原始样本或正在运行的游戏。

## 为什么“模块基址+偏移”改了却没有加快攻击

若地址是 Cheat Engine 扫描列表里的绿色 `模块名+偏移`，[CE 官方说明](https://wiki.cheatengine.org/index.php?title=Cheat_Engine:Memory_Scanning)表明绿色表示地址落在已装载模块中的静态位置；这只解决再次找到该地址的问题，不证明该位置就是最终角色攻速。它也可能是指向动态角色对象的指针、收到的状态缓存或显示用数据。先确认基址对应的模块和样本哈希，再看偏移所在对象、数据宽度，以及改动后究竟哪一层没有变化。`Game.dll+RVA` 指模块中的静态位置；`CharacterObject指针+字段偏移` 指一次运行中的对象。把后者直接加到 Game.dll 基址，会写到完全不同的位置。

| 如果改的是 | 当前可解释的现象 | 需要核对的事实 |
| --- | --- | --- |
| `Game.dll+D71BE0` | 这是收到的状态块 `D71B78+68` 中的 **uint16 间隔候选缓存**；`S_STATUS→42DD90` 可再次覆盖它。增大间隔按现有本地比较只会更难通过。 | 同哈希样本、16位写入、修改前后读回值、状态更新后是否恢复、`06A16D` 分支是否改变。旧版服务端源码将对应包字段称为 `ATTACK_SPEED`，但当前 Classic 的单位和线上规则仍需实测。 |
| CharacterObject `+508/+50A` 或 `+4F4` | 这组输入只证明会改变 `4BC390` 的 `cattack` 动画比例；改变画面播放速度不能证明本地攻击请求或服务端伤害次数增加。 | 对象类型与指针、动画实际持续时间、每次 `06A0B0` 到达及通过次数、实际伤害事件。 |
| CharacterObject `+1C88` | 这是本地请求门槛使用的上次计时值，不是“最终攻速”；`05D140` 可调整它，成功请求又将它写成当前计时值。单次改动可能只影响一次比较。 | 对同一对象记录修改前后、`05D140` 后和 `06A350` 后的值，并观察 `06A16D` 的分支。 |
| 物品实例 `+1C8/+1CC`、武器记录 `+1BE` 或 SkillItem `+50/+54` | 分别是物品属性缓存、武器基础间隔及动作/技能计时，不能直接当作角色最终普通攻击频率。 | 看目标地址的对象来源与使用函数，避免仅凭偏移相同就认作 Player 字段。 |

可把“没有加快”拆成三个可观测结果：**挥动动画未变、挥动变快但本地请求次数未增加、本地请求变多但有效伤害次数未增加**。第一种先核对对象/动画分支及覆盖写入；第二种核对 `061C20→042860→06A0B0` 和本地门槛；第三种要核对服务器确认。归档的旧版服务端源码中，请求并不携带客户端宣称的最终攻速，服务端另按自己的属性重算值检查间隔；这能解释“只改客户端缓存不增加伤害”的一种机制，但不是当前线上服务器已被实测的结论。没有实际修改地址、类型、数值和这三种现象的区分，不能把单一原因断言成已证实。

直接用 Game.dll 原始比较指令做的[同输入离线对照](../evidence/continuous/20261013-animation-interface/offline-attack-cache-gate-experiments.json)进一步限定了它的作用：构造上次计时1000、当前1150时，缓存间隔200使本地比较拒绝；**只把 `D71BE0` 的uint16改成100，同一比较改为通过**。若随后构造一次成功请求将上次计时变成1150，则当前1200又被100间隔拒绝，到1251才通过。这证明静态缓存修改可以影响**这个局部比较**，也证明它不是一次改完就能跳过下一次时间更新的“永久攻速”。实验没有运行前置保护计时、`05D140`、动作触发、请求发送或服务端。

## 按“是否被消费”判断改值能否生效

| 想看到的效果 | 改值必须穿过的已知关口 | 单改绿色模块地址的典型断点 |
| --- | --- | --- |
| 角色本地移动向量改变 | CharacterObject 正确对象的 `+6C8/+6CC/+6D0` 关系 → Game `4BBA10` 的速度读取 → 关联物理对象类型1/模式3运动输入 | `Game.dll+D71CA0` 是另一个本地缓存；只改它不等于改了 Game 消费者读取的对象字段。下次 `460440/4BF3C0` 也可能重算。 |
| 角色本地动作变快 | Game `4BC390` 对**当前动作名称/模型**算出的倍率 → `493940` 或其他实际动作路径 → 对应 CryAnimation 实例和层的 `+360` 设置 | 改错模型/动作、只改显示字段、对象指针不对、层参数无效、改后被下一次动作重设，都不能由 CE 绿色地址本身排除。 |
| 本地普通攻击请求更频繁 | 动作状态 `061C20→042860` 实际走到 `06A0B0` → 经过 `05D140` 调整后的 `+1C88` 与 `D71BE0` 比较 → 后续目标/动作和发送条件 | 只改动画比例不会消除本地门槛；只改 `+1C88` 也会被调整或成功请求后的时间写回。只改收到的 `D71BE0` 会被状态同步覆盖。 |
| 有效伤害次数增加 | 上述本地路径成立，并由当前测试服实际接收与结算 | 客户端动画和内存读回无法证明服务端规则变化。已归档的旧版服务端另按自己的 ATTACK_SPEED 重算值限制攻击；当前目标服仍须用同场景结果核对。 |

因此，**静态基址可以是定位入口，但“值读回成功”不是“效果生效”**。针对同一次改动，应按时间顺序保存写入后的值、下一次状态/动作更新后的值、Game 消费者实际读取值、CryAnimation 或 CryPhysics 接收值、本地请求次数和测试服接受次数。缺任一层就把结论停在那一层；仅有这份归档无法替代一次运行中的指针、模块哈希、动作层和服务端结果。

## 不应当当作最终攻速的值

`396E80` 返回查询记录 `+1BE` 的uint16武器基础间隔。`1D90C0` 将它除1000后格式化显示，`1DA810` 用它划分快慢档。改变这一显示链，尚不能证明攻击调度变化。

`3B2500` 写 SkillItem `+50/+54` 的共享冷却表示，并可能按武器间隔缩放冷却。这不是上述 CharacterObject `+1C88` 的攻击门槛。`attackDelay=29` 是属性编号，不是 `Player+29` 的攻速地址；`max_speed` 的一条已读路径属于boid群集配置，也不是玩家移速上限。
