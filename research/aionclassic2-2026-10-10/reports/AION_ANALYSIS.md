### 地址的含义

以下没有特别标明的模块地址均为 **RVA（模块内相对地址）**。运行时地址应为 `实际加载基址 + RVA`，本轮未观察实际加载基址。PE 中 Aion.bin 的首选基址为 `0x140000000`，其余三个模块为 `0x180000000`；不能将其假定为 ASLR 后的实际地址。

`对象 + 0x119C` 是对象成员偏移，`Game.dll + 0xD647C0` 是模块内位置，两者不是同一类“偏移”。JSON 每个地址尽量同时记录 RVA、首选 VA、文件偏移、所属节。没有文件原始数据支撑的零初始化区域，文件偏移记为 null。

### 保护入口与第一层还原

三个受保护模块的 PE 导入目录目前均仅显示 `kernel32.dll!lstrcpy`。它们存在类似的跳转与解码结构，原始代码、字符串和 RTTI 仍有大量可读部分；不能笼统认为整个文件都被加密。保护器品牌和版本未确认。

| 模块 | 文件入口 RVA | 入口跳转链中的另外两处 | 第一层解码桩 RVA | 被解码区 RVA | 解码后继续地址 | 下一跳 RVA |
|---|---|---|---|---|---|---|
| Aion.bin | `0x5EE000` | `0x5EE00A → 0x5F000F` | `0x5E2000` | `0x149000` | `0x149014` | `0x14A835` |
| Game.dll | `0x141A000` | `0x141A00A → 0x141C00F` | `0x13C1000` | `0xE26000` | `0xE26014` | `0xE277D5` |
| CrySystem.dll | `0x77B000` | `0x77B00A → 0x77D00F` | `0x762000` | `0x2BE000` | `0x2BE014` | `0x2BF7F1` |

解码桩通过 call/pop 取得自身位置，计算目标缓冲区；随后对 0x1000 字节、共 1024 个小端 uint32 执行：

```text
明文 DWORD = ((原 DWORD XOR xor_key) + add_key) mod 2^32
```

| 模块 | xor_key | add_key |
|---|---|---|
| Aion.bin | `0x76145AC7` | `0x6D21FE52` |
| Game.dll | `0x4AEA85EB` | `0x25DCB9BB` |
| CrySystem.dll | `0x0C55E334` | `0x66768119` |

关键依据：桩内 `mov ebx,0x1000`、`shr ecx,2`、`xor dword ptr [rsi],eax`、`add dword ptr [rsi],ebx`、每轮地址增加 4。上述两个密钥来自实际压栈立即数。脚本核验这些关键指令后才变换数据。

三个 4 KB 结果均已保存为独立 `.bin`，源 PE 未修改。逆变换逐字节匹配源数据，解码区 `+0x14` 出现有效的直接跳转；下一跳在原文件中可读，开始保存寄存器并计算保护器上下文地址。逆变换验证证明字节变换可复现，不等于重建程序可运行。

产物：`exports/protection-stage1/`。JSON 包括每份输出的 SHA-256。第一层区域包含数据，顺序反汇编产生的 `add [rax],al` 等文本不是已执行路径；应以 `entry-chain` 和明确分支为准。下一阶段仅导出入口窗口，尚未还原完整控制流或原始导入解析。

### 玩家相关解析链

`CXGame` 主虚表字节偏移 `+0x1E0`（slot 60）指向 `Game.dll + 0x2B720`。该叶函数：

1. 从 `Game.dll + 0xD6CB08` 读取 16 位 ID，零值直接失败。
2. 从 `Game.dll + 0x94C7B0` 读取系统对象指针，空值直接失败。
3. 经该对象虚表 `+0x30` 以 ID 查找实体。系统对象的精确动态类型尚未验证。
4. 调用者将实体传给 `Game.dll + 0x4F9810`；该函数通过实体虚表 `+0xB8` 取得容器，再通过容器虚表 `+0x50`、接口编号 2 取得组件指针。

`GetPlayerPos` 和玩家属性快照函数都使用这条链，因此它是“本地玩家实体/组件解析链”的强静态证据。实际 ID、系统指针、组件指针和动态 RTTI 仍需在运行时确认；此处没有提供一个伪造的固定玩家堆地址。

## 攻击速度实战第一课：从名称追到取值过程

用户此前观察到：攻速可能并非固定地址直接存放的最终值，而是在使用前经过隐藏计算。本轮把这条线索保留为待验证假设；当前证据还不能确认具体加密方式、隐藏地址或计算公式。

### 已证实的三类线索

| 字符串 | Game.dll RVA | 当前发现 |
|---|---|---|
| UTF-16 `attackDelay` | `0x774918` | 名称转换代码和两类枚举表引用 |
| UTF-16 `attack_delay` | `0x776A50` | 资源字段名与数据记录描述表 |
| UTF-16 `AttackSpeed` | `0x7F6AA8` | 另一组名称表引用；其运行时用途尚未关联 |

不要仅因为名字相近就将三者认作同一个内存字段。尤其不能把属性编号当成员偏移。

### 路径一：属性名称转换成编号

在 `Game.dll + 0x86450` 所在代码中，`0x868BD` 引用 `attackDelay`。字符串比较匹配后，`0x868D1` 设置 `eax=0x1D`，然后把 AX 写入输出位置。表 `0x94E2F0` 也存放该名称指针，其后 `0x94E2F8` 的值为 `0x1D`，两项证据相互印证。

这证明该转换上下文中的 `attackDelay` 属性编号为 **29**。不证明 `Player+29` 是攻速，也不证明整程序所有出现立即数 29 的位置都处理攻速。扫描得到的 73 处参数立即数候选中，许多明显用于长度、其他枚举或通用类型分派，不能全部计为攻速引用。

### 路径二：基础攻击间隔记录的读取

`0x6ECAE8` 是 `attack_delay` 名称指针；后续描述数据中出现位移 `0x1BE` 和宽度 `2`。相邻 `attack_range`、`hit_count` 记录也采用相似布局。

更直接的证据来自 `Game.dll + 0x396E80`：

```text
保存 EDX 中的查询 ID
调用 0xE7EC0 查询记录，参数之一为 0x210
如果找不到，经过 0xE7D30 取得备用查询参数后重试
如果仍找不到，返回 0
找到记录时，返回 zero_extend(uint16(record + 0x1BE))
```

关键指令为 `0x396EC6: movzx eax, word ptr [rax+0x1BE]`。这里的 RAX 是查询函数刚返回的记录指针，不是已经确认的角色对象基址。参数 0x210 的精确含义尚未恢复，不能仅凭数值断言它就是完整结构体大小。

目前提取到五个直接调用点：`0x1D90E8`、`0x1DA84D`、`0x1DC1BB`、`0x1DC1C6`、`0x3B25B0`。查询记录及调用者的上下文支持“物品/武器基础攻击间隔”的解释，但尚未证明它代表带全部加成后的最终攻速。

### 路径三：显示时的换算

`Game.dll + 0x1D90C0` 从输入记录 `+0xC` 取得 ID，调用上述读取函数，然后执行：

```asm
movzx eax, ax
movd xmm1, eax
cvtdq2ps xmm1, xmm1
divss xmm1, dword ptr [Game.dll + 0x8754A0]
```

`0x8754A0` 的 float32 原始字节为 `00 00 7A 44`，实际值为 **1000.0**。后面代码将结果转成 double 并传给格式化函数。因此，字段从类似毫秒的整数转换成秒数显示，是有指令和常数支撑的解释；这个函数本身不等于最终攻击调度器。

资源交叉核对：已解包的通用物品表中，8,188 项具有 `attack_delay` 字段。例如剑 `100000001` 为 1400、锤 `100100001` 为 1500、匕首 `100200001` 为 1200。与上面显示换算相结合，分别得到 1.4、1.5、1.2。这里演示的是基础资源值，不能据此推断实际战斗中一定按这些间隔攻击。

### 尚未坐实的计算路径

`0x3B25B0` 的调用者沿本地实体链获取组件，经组件 `+0x1010` 和另一个函数取得查询 ID，再读取基础间隔。其后另一段代码出现“基础间隔 / 常数 × 另一个记录值”的浮点运算，并写入某记录的 `+0x50`、`+0x54`；还会调用保护区域中的 `0x1244AE3`。

这是真实的后续数值处理线索，但该分支可能属于技能或其他计时子系统。尚不能把它命名为最终普通攻击公式，也不能因为调用进入保护区域，就断言攻速值经过加密。还需确认调用者、参数、写回对象和使用这些结果的代码。

返回的是差值，不能据此把其中任意临时寄存器理解为最终角色攻速。

### 逐步还原当前分支的计算，不给未知参数强行命名

`0x3B2500` 的第三、第四个整数参数分别保存在 ESI 和 R12D。先查询目标对象，随后：

```text
duration_bits = low32(arg3 * arg4)
target[+0x50] = duration_bits
target[+0x54] = low32(protected_return() + duration_bits)

base_delay = 1000
if local_component exists:
    query_id = map_id(component, component[+0x1010], 0)
    base_delay = uint16(get_base_delay(query_id))

if arg3 != 0:
    group_key = queried_record[+0xE0]  // 查询失败时为 0
    for associated object in group:
        skip null object and original target
        query and copy its 0x7D8-byte record to a local buffer
        if byte(record[+0xD0]) == 0:
            raw_duration_bits = dword(record[+0xD4])
        else:
            raw_duration_bits = trunc_to_int32(
                float32(base_delay) / 1000.0 * float32(uint32(record[+0xD4])))
        duration_bits = low32(raw_duration_bits * arg4)
        object[+0x50] = duration_bits
        object[+0x54] = low32(protected_return() + duration_bits)
```

这是人工恢复的局部语义，不是源代码；浮点表达式对应 SSE 单精度运算，极端输入的转换异常值、溢出和回绕不作业务含义推断。这里 `record+0xD0/+0xD4` 来源于复制目的地址 `rsp+0x20`，所以实际指令读取的 `rsp+0xF0/+0xF4` 必须先减去这 0x20。不能把栈位置误写成角色字段。

`+0x50` 暂记为“时长候选”，`+0x54` 暂记为“截止时刻候选”：后者由一个保护区域函数的返回值加时长构成。但 `0x1244AE3` 的内部语义、时钟来源与单位尚未确认，不能改名为已确认的 GetTickCount，也不能据此断言是在解密攻速。另一入口 `0x3B27D0` 能直接按输入值写 `+0x54`，说明上述路径也不是该字段的唯一写入来源。

教学算例（非运行实测）：若某关联记录满足缩放分支，基础间隔为 1400、记录值为 2000、arg4 为 1，则表达式的数学近似为 `1400/1000×2000=2800`；实际仍按单精度及截断处理。这个 2800 是该分支的计时结果，不能称为角色面板攻速。

## 攻击速度实战第三课：资源解析、百分比位标记与有符号数值（2026-10-11）

本轮得到两条新的静态证据链：一条是技能效果参数如何进入原生记录；另一条是物品攻速加成如何从文本转换为带标记的数值，再进入物品属性缓存和显示函数。两者尚未连接到角色最终攻速聚合器，不能混作一个公式。样本与前两课相同，没有运行 DLL 或附加游戏。

### StatUp 类型与保留字段的实际布局

`0x53C060` 从 `0x6C5880` 起遍历 173 个效果名称指针，匹配后返回数组下标，找不到返回 `0xAD`。本表下标 8 是 `StatUp`，下标 9 是 `StatDown`。编号只针对该效果类型上下文；`attackDelay=29` 属于另一张属性编号表。

技能 XML 解析器会动态生成 `effect%d_reserved%d` 字段名，并处理四个效果，每个效果遍历 18 个保留字段。匹配后将字段文本交给 `0x7D810`；该函数可查找已有宽字符串或分配副本，返回指针，解析器将它存入参数数组。没有在这个通用保存步骤里把 `reserved13=attackDelay` 直接变成编号 29，也没有在这里把 `reserved2=20` 直接变成百分比。

一个关键的地址换算：解析函数的技能记录始于 **RBP−0x10**，由 `0x53C737…0x53C73F` 传给记录初始化函数。因此，`[rbp+0x108]` 对应记录 `+0x118`，不能直接写成记录 `+0x108`。

| XML 内容 | 原生技能记录中的位置 | 本轮证据 |
|---|---|---|
| `delay_type` | `+0xD0`，4 字节 | `0x53D7C3` 写 `[rbp+0xC0]` |
| `delay_time` | `+0xD4`，4 字节 | `0x53D857` 写 `[rbp+0xC4]` |
| `delay_id` | `+0xE0`，4 字节 | `0x53D80D` 写 `[rbp+0xD0]` |
| `effect1_type…effect4_type` | `+0x114 + 4*i`，4 字节 | 四个解析写入，与 `0x541A00` 读取公式一致 |
| `effectN_reservedM` | `+0x128 + 0xB8*i + 8*j`，8 字节指针 | 动态字段名、`0x5405AC` 写入、`0x541A80` 读取相互印证 |

其中 `i=N−1`，`j=M−1`。例如技能 335 的第二效果：类型在记录 `+0x118`；`reserved2` 的文本指针槽在 `+0x1E8`；`reserved13` 的文本指针槽在 `+0x240`。后两者指向类似 `20`、`attackDelay` 的宽字符串，不是角色对象内的实时数值。

读取接口也已找到：`0x541A00` 取效果类型；`0x541A80` 取某个保留字段指针；`0x541B30` 取一个效果的参数区起始地址。地址均为 Game.dll RVA，不是源码符号名。

这同时补实了第二课的未知映射：技能计时分支的 `+0xD0/+0xD4/+0xE0` 对应 `delay_type/delay_time/delay_id`。但读取计时分支检查的是 `delay_type` 的低字节；上述映射不等于已恢复全部 delay_type 枚举语义。

### 找到一条真正的“数值不是原样存储”的路径

物品 XML 中存在明确带 `%` 的字段，例如 `bonus_attr2=attackDelay 3%`；套装中有 `fullset_bonus=attackDelay 8%;speed 10%;flyspeed 6%;maxHp 500`。本次完整扫描得到：

- `client_items.xml`：1,913 个字段匹配 `attackDelay 数字%`。
- `client_setitem.xml`：16 个字段匹配。
- `client_skills.xml`：该文本模式为 0；技能效果使用另一套字段表示。这个 0 不表示技能没有攻速效果。

这些是匹配字段计数，不是不同物品数，也没有覆盖所有可能的表达形式。

`0x394C2F` 所在解析片段识别 `bonus_attr` 字段，取属性名称和数值文本。名称转换仍调用 `0x86450`。遇到末尾字符 `%`（`0x25`）时，去掉字符后对数值执行 `OR 0x8000`；非百分比分支执行 `AND 0x7FFF`。属性编号和带标记数值分别写入物品记录：

```text
uint8  attribute_id[12]  位于 record + 0xD8
uint16 encoded_value[12] 位于 record + 0xE4
```

不是把一个 `%` 字符塞入内存数值，而是使用 16 位字的 bit 15 表示百分比。套装解析器 `0x3930C0` 也有相同的高位标记操作，并处理分号分隔的多项属性。

### 拆开位运算：低 15 位是有符号数

`0x3A0BE0` 查询并复制物品资源记录，随后展开 12 个加成槽。每个有效属性编号使用相同的位运算。第一槽的关键指令位于 `0x3A0C1E…0x3A0C50`：

```text
percent_flag = raw16 >> 15
value = sign_extend_15(raw16 & 0x7FFF)
```

第二行是对实际 `movsx / add dx,dx / xor / and / cwde / xor` 序列的等价简化。它不只是 `raw16 & 0x7FFF`：**bit 14 是数值部分的符号位**。如果忽略符号扩展，负加成会被误读成一个很大的正数。

| 原始 16 位字 | 百分比标记 | 解出的有符号数值 |
|---|---:|---:|
| `0x8003` | 1 | 3 |
| `0x8008` | 1 | 8 |
| `0x8012` | 1 | 18 |
| `0x01F4` | 0 | 500 |
| `0x7FF6` | 0 | −10 |
| `0xFFF6` | 1 | −10 |

这张表是对观察到的指令序列做的算术复现，不是实时游戏内存采样。对全部 65,536 个 16 位输入逐一比较，简化表达式与指令模型结果完全一致。该实验不执行游戏代码。

这里的若干 XOR 用于提取并符号扩展位字段，有完整、可验证的数值含义。不能仅凭出现 XOR 就断言它是攻速加密；也不能把这一条物品表示的结论推广到整个客户端。

### 展开后的值属于 InventoryItem

构造函数 `0x3A0030` 写入虚表 `0x82FC38`，RTTI 名称为 `InventoryItem`。该虚表的 `+0x20` 槽指向 `0x3A0250`，后者保存物品 ID，并在 `0x3A06E5` 尾跳转到属性展开函数 `0x3A0BE0`。这是将展开结果与物品对象关联的证据，不是把一个偏移猜成 Player 字段。

展开时按属性编号索引，每项步长 8 字节：

```text
int32 value       写入 item + 0xE0 + attribute_id * 8
uint8 percentFlag 写入 item + 0xE4 + attribute_id * 8
```

在 `attackDelay` 编号为 29 的上下文中，算得值槽为该物品对象 `+0x1C8`，标记槽为 `+0x1CC`。这是**物品属性缓存内的相对位置**；没有得到固定堆地址、玩家指针链或角色最终攻速。单独看到另一个对象也访问 `+0x1C8`，不能认作相同字段。

### 继续追到显示端：百分比与绝对间隔分别处理

`0x1D9370` 从输入对象的上述数组读取数值和标记，并格式化到输出字符串：

- 属性 29 且百分比标记非零：选择 `%s%d%%`，显示整数百分比，前缀另按数值正负处理。
- 属性 29 且标记为零：整数转为 float，乘以 `0x874B24` 处的 float32 常数（约 0.001），再用 `%s%.1f` 格式化。
- 数值为零时在更早的分支退出，不生成上述非零属性文本。

这给百分比标记的解释提供了消费端证据。链条现为：

```text
物品/套装加成文本
  → 属性名称转编号
  → 带百分比标记的 16 位值
  → InventoryItem 的数值 + 标记缓存
  → 根据标记选择百分比或绝对间隔显示
```

最后一个已确认使用者是属性文本格式化函数，不是最终攻击调度器。

### 对你以前 CE 分析经验的具体解释

如果看到“攻速加成 18%”，相关表示可能是文本 `attackDelay 18%`、资源中的 16 位 `0x8012`，或物品对象内分开存放的整数 18 与标记 1。它们与基础攻击间隔 1400、显示间隔 1.4、角色最终攻击间隔属于不同层次。直接搜索 float 18 或 float 1.4，未必命中参与计算的那份数据。

现在能确认本版本至少有这种位字段编码与按需转换，但还不能说它就是你以前遇到的那条隐藏攻速计算。技能 StatUp 的保留字段也不能直接套用物品的 16 位编码规则。

- 消息名称注册函数内能确认`S_REQUEST_TELEPORT`、`C_ACCEPT_TELEPORT`、`S_MOVE_NEW`、`C_MOVE_NEW`、`S_MOVEBACK`、`C_MOVEBACK`。`0x316E18`是传送名称注册引用，`0x31A8F3`是接受传送名称注册引用。
- **名称注册不是处理函数**。目前没有证明消息字段布局、前后缀方向、服务器信任范围或MOVEBACK的全部语义。不能把名称常量当成可发送的有效协议操作。

下一步有判别力的证据是：同版本正常技能的位移是否有技能消耗/冷却，位置是否被其他角色或后续交互认可，是否发生回正，以及客户端哪一个消费者应用收到的位置。本轮未进行这些在线观察，因此“修改可实现任意瞬移”尚无结论。若只有本机画面移动，不能证明战斗距离判定也移动。

### 3. 神石概率：从原始数值到中文说明

```text
对应概率小数 = 原始值 / 1000
```

其余14条缺可用于该检查的数字说明，不记为一致，也没有补造说明。这个结果证明资源数值与说明使用的尺度，不证明实际掷骰概率。

### 4. 装备强化概率：已恢复的客户端显示公式

这部分有完整的原生计算与显示链，证据强于仅按字段名字推断。全部地址为该SHA对应Game.dll的RVA，运行时模块基址不是固定的0x180000000。

```text
DlgEnchant查找控件 "enchant_prob"
  0x17036E引用名称；0x17037E保存控件指针到对话框+0x540
→ 0x171F70及后续片段检查控件和功能条件
→ 选择装备、强化材料、辅助剂
→ 0x172030调用0x316610
→ 0x172050乘float32(0.1)
→ %g%%格式化，并经控件虚函数设置文字
```

对话框的`+0x540`是UI控件指针，不是概率或玩家属性。附近其他类也有相同偏移，已区分语境。

计算输入及证据：

| 输入 | 原生证据 |
|---|---|
| 装备品质q | `0x3967A0`读取物品模板`+0x1E1`字节；描述表指向quality及转换器`0x392DD0` |
| 装备/强化石等级L | `0x396D00`读取模板`+0x1ED`字节；描述表明确为level |
| 阶段n | `0x3166E5`读取装备实例`+0xA9`字节，随后加1；按强化UI语境解释为本次目标强化阶段，未运行时核验 |
| 辅助剂加成A | `0x397BD0`读取模板`+0x1DC`的uint16；描述表明确为sub_enchant_material_effect |

材料分类器`0x16F200`把物品ID166000000至166099999分入返回1的路径，UI在此调用上述公式；167000000至167099999走另一条路径。不能把装备强化和魔石强化混为同一个计算。

令`d = 强化石level - 装备level`，`k[q]`如下，`clamp(x,a,b)=min(max(x,a),b)`，`trunc0`为向零截断。仅对已观察分支n=1..20写出公式：

```text
n <= 10: B = clamp(k[q] * (d + 10), 0, 800)
11 <= n <= 20: B = clamp(trunc0(k[q] * (d + 10) / 2), 0, 500)
R = clamp(B + A, 0, 1000)
显示百分数 ≈ R / 10
```

实际显示使用float32的0.1再格式化；公式为数学简写。q在1..6之外，n<=20时该函数有提前返回0的分支。n>20的代码行为也存在，但不能据此声称允许强化到更高等级，本节模型不开放这个输入。

| quality | 编号 | k（原始千分单位） | n≤10达到基础80%所需最小d | n=11..20达到基础50%所需最小d |
|---|---:|---:|---:|---:|
| common | 1 | 60 | 4 | 7 |
| rare | 2 | 40 | 10 | 15 |
| legend | 3 | 30 | 17 | 24 |
| unique | 4 | 20 | 30 | 40 |
| epic | 5 | 15 | 44 | 57 |
| mythic | 6 | 10 | 70 | 90 |

上表“阈值”是这个UI函数中基础项封顶的等级差，不是服务器实测成功率阈值。上限常量分别为0x320=800、0x1F4=500；先截断基础值，再加辅助剂，最后整体截断到0x3E8=1000。

普通Probability辅助剂的原始50/100/150在这条加法路径中对应**显示概率增加5/10/15个百分点**。不是50%/100%/150%，也不是把现有概率乘1.05/1.10/1.15。UI之前的选择资格、消耗数量与可强化最高等级是其他约束，不能只看这一个函数。

|---|---:|---:|---:|---:|

实际帮助：该模型能解释为什么更高级石头在某阶段不再增加客户端显示值，以及跨阶段时显示概率可能下降；可以用来定位UI是否按预期计算。不能用这些尚未与服务器对照的数据承诺某次成功，或把模型输出直接当成花费预算。

辅助剂表有18条记录：普通Probability类型11条（含活动条目）；cash_option_prob类型7条（其中3条名称明确为test）。例如166150003名为“唯一用100%魔石强化辅助剂”，raw=1000，**只描述魔石强化用途**，不能套成装备强化到任何等级100%成功。测试物品的100%同样不证明正式服开放。

排除的误导线索：`successenchant`字符串在`0x537ECF`属于type枚举解析，与questclear、hunt、joinlegion、useportal等并列，匹配后写入编号13。它是成功强化事件类型线索，不是“强化成功率=13”。

### 1. RandomMoveLoc.Distance 的取值已有代码证据

名称表不是每个字符串各有一个直接调用者。效果表 `0x6C5880` 中 RandomMoveLoc 为编号82；属性表 `0x6E2190` 中 Distance 为编号33。解析器引用的是表基址，单独搜字符串交叉引用会漏掉这一层。

实际链条：

`说明文字 → 0x28D490拆分效果序号/类型/属性 → 0x28D6C0主格式化路径 → 0x541A00核对效果类型 → 0x541B30取reserved参数 → 0x28B960分发 → 0x28C468检查Distance → 0x28A420格式化`

`0x28B960` 先用字节映射表 `0x28CA20` 压缩效果编号，再读32位RVA跳转表 `0x28C904`。RandomMoveLoc的映射字节为39，进入 `0x28C468`，不是简单的“编号×函数指针”。

在 `0x28A420`，参数指针来自上下文+0x30：读取reserved2（参数块+8）和reserved1（参数块+0），分别转换，再在 `0x28A484` 相乘、`0x28A497` 相加：

```text
Distance提示整数 = C(reserved1) × L + C(reserved2)
L = 格式化上下文的int32字段+0x1C
```

其中C表示间接调用槽 `0x6BC170` 返回的整数；空字符串指针明确按0处理。该槽在磁盘里的值不是可直接解析的正常导入函数地址，尚未确认具体转换函数，不能直接命名为 `_wtoi`。L由主格式化路径传入，在普通占位符分支沿调用者参数传播；还不能保证所有语法下它都等于角色等级或技能等级。

| 技能ID | 名称 | reserved1 | reserved2 | reserved3 | 已证明的范围 |

| 1424 | 时空跳跃 | 0 | 30 | 1 | 提示依赖前两个参数，通常的十进制转换解释得到30 |

### 2. 消息名称已关联到真实分发函数

RTTI确定 `ServerToClientRouter`，其虚表槽5（槽地址 `0x8381E0`）指向 `0x426F70`。该函数读取消息对象+0x14的uint16编号，使用 `0x42BBB4` 的32位RVA表分发。名称注册器 `0x316950` 与分发编号已关联245条名称。

| 名称 | 内部编号 | 分发入口 | 已追到的消费者 |
|---|---:|---|---|
| S_STATUS | 0x01 | 0x427E0F | 0x42DD90，状态块同步 |
| S_STATUS_OTHER | 0x02 | 0x427E2A | 0x4344B0，语义尚未展开 |
| S_HIT_POINT | 0x03 | 0x427E45 | 0x488F00，HP组件更新 |
| S_MANA_POINT | 0x04 | 0x427FC1 | MP缓存更新 |
| S_REQUEST_TELEPORT | 0x14 | 0x427BD2 | 0x51C80，模式分支/事件/定时回调 |
| S_ATTACK | 0x36 | 0x4286DE | 0x430D20，再经Player虚表+0x288到0x480890 |
| S_MOVE_NEW | 0x37 | 0x428D45 | 已定位分支，尚未还原全部逻辑 |
| S_MOVE_OBJECT | 0x38 | 0x4279AC | 已定位分支，尚未还原全部逻辑 |
| S_ATTACK_RESULT | 0x73 | 0x4277FA | Player虚表+0x480到0x2DA70 |
| S_MOVEBACK | 0xC3 | 0x427A09 | 0x477210，查找/更新动作位置或建立后备动作 |

这里的数据起点是 `消息对象的指针字段+0x18 + 有符号位移字段+0x20`。这是客户端内部解码缓冲区表示，不是加密网络包的直接偏移。名称已注册也不代表每条都有独立实现，例如S_CUR_STATUS的编号0xE4在所查表中落入缺省分支。

**对MOVEBACK的修正：** `0x477210` 搜索角色组件+0x1110/+0x1118、+0x1128/+0x1130等队列，按标识匹配后可写记录+8/+0xC/+0x10三个坐标并设置标志；另外存在构造0xC02描述符、调用 `0x475BF0` 的后备路径。单凭名称不能称它为“反作弊拉回”。

新的队列交叉证据：S_ATTACK进入 `0x480890` 后构造动作记录，并在 `0x480B9E` 起追加到组件+0x1110/+0x1118。它正是MOVEBACK搜索的队列之一。因此已证实攻击动作接收与位置更新之间存在数据结构联系；仍未证明该链专属于RandomMoveLoc。

`0x51C80` 的遥移处理还涉及模式号、事件0x428/0x427/0x415及定时回调。尚未确认虚函数事件的完整消费端，不能把某个事件调用直接命名为“任意坐标写入”。

### 3. 收到的属性、缓存和界面快照不是同一层

```text
S_STATUS → 0x42DD90 → 0x4FCB00更新组件 + 全局状态缓存
S_HIT_POINT → 0x427E45 → HP缓存 + 0x488F00更新组件
全局缓存 → 0x368E50生成快照 → 部分字段由组件再次覆盖 → 界面/提示使用
```

`0x42DD90` 从内部载荷+8取得0xC8字节状态块，经栈中转写入 `0xD71B78` 起的缓存。不是完全原样复制：块内+0x50/+0x54等时间候选字段先乘1000，扩展区域另行处理。该缩放还不能给字段冠以“攻击间隔”或“施法时间”。

| 数据 | 同步/读取行为 | 解释边界 |
|---|---|---|
| HP当前/最大缓存 | S_HIT_POINT载荷+0/+4写入0xD71BB8/0xD71BB4 | 已确认接收来源 |
| MP当前/最大缓存 | S_MANA_POINT载荷+0/+4写入0xD71BC0/0xD71BBC | 已确认接收来源 |
| 组件HP | 0x488F00写组件+0x11A4当前、+0x11A0最大 | 这是该组件布局，不能套用于任意对象 |
| 组件另一份HP | 组件+0x1190为0时，才把当前值写入+0x119C | 控制标志含义尚未确认 |
| 输出快照HP | 0x368E50先复制缓存，再把快照+0x40改为max(组件+0x119C,0) | 显示用快照不一定等于同一时刻的原始缓存 |

所以“搜到某个数值”只证明某处保存了它，尚不能证明是最终战斗属性、唯一真值或服务器认可值。前面发现的InventoryItem属性缓存同样不能直接跳推为玩家字段。

另有一条新的攻速相关候选：`0x430D20` 读取S_ATTACK内部载荷+5的uint16，转float并除以1000.0，经虚调用传到 `0x480890`，存入新动作记录+8。已确认**收到的数值→缩放→动作记录**，但它究竟是攻击间隔、表现时长还是其他时间量尚未证明，不将其发布为“最终攻速地址”。

### 4. 技能射程有消费者，但不能等同服务器允许攻击距离

解析器中 `first_target_valid_distance` 写技能记录float+0x724；`add_wpn_range` 写记录int+0x72C。记录基点为RBP-0x10，不能直接把栈偏移当记录偏移。

`0x19B20` 的计算可写为（正常有限浮点输入）：

```text
r = skill.float_724
若 skill.int_72C != 0：r += 状态缓存float(0xD71BDC)
输出1 = r
输出2 = max(r - (对象.int_AEC != 0 ? 1.0 : 0.0), 1.0)
```

查不到技能记录时，初始r为5.0。`0xD71BDC` 位于S_STATUS同步块的+0x64，说明这条客户端计算会组合技能表与收到的角色状态。+0xAEC标志含义未知；这段函数内未见上限，不等于全流程没有上限。

更关键的是收到的攻击结果：S_ATTACK_RESULT在 `0x42780D` 读取有符号结果字节，通过Player虚表+0x480调用 `0x2DA70`，再由分支选择本地化消息：

| 收到的结果码 | 文本ID | 本版本中文提示 |
|---:|---:|---|
| 1 | 1300115 | 攻击者或攻击对象在其他地区。 |
| 2 | 1300116 | 不是正确的对象。 |
| 4 | 1300032 | 对象距离太远。 |
| 5 | 1300033 | 中间有障碍物，无法攻击。 |
| 6 | 1300828 | 距离太近，无法进行攻击。 |

码3落入缺省返回，码7有另一条动作处理分支，不能补造对应文字。此链证明客户端能够接收并显示上述结果原因；服务器何时产生它们、阈值及碰撞计算方法仍不可从这些提示推出。仅修改本地射程计算并不能由本报告证明会改变服务器的认可结果。

### 5. 伤害说明已恢复三条算术路径

这是技能说明占位符路径。记 `ri` 为当前效果第i个reserved文本，C为上文间接转换函数；L为上下文+0x1C。

`X0 = uint16(状态快照+0)`，`X8 = uint16(状态快照+8)`。这两个字段来自 `0x368E50` 生成的状态快照；尚未独立核实字段名称，因此不直接给它们套上“力量”“知识”的名字。

`Wmin/Wmax` 是主说明函数放入上下文+0x14/+0x18的两个端点，关联读取器 `0x396D60/0x396DC0` 分别读取物品模板uint16+0x1B8/+0x1BA。它们不是已证明包含全部Buff的玩家最终攻击上下限。

物理效果SkillATK_Instant的MinDamage/MaxDamage（属性号56/54）分别进入 `0x289EC0/0x28A000`：

```text
A = C(r1) × L + C(r2)
B = C(r3) × L + C(r4)
提示值 = trunc0_f32( (A/100 + ((X0-100)/200 + 1)) × W + B )
MinDamage使用Wmin；MaxDamage使用Wmax。
```

魔法效果SpellATK_Instant的FixDamage（属性号41）进入 `0x28A340`：

```text
A = C(r1) × L + C(r2)
提示值 = trunc0_f32( A × ((X8-100)/100 + 1) )
```

`trunc0_f32` 表示按实际SSE单精度运算次序计算，最后CVTTSS2SI向零截断；对应指令为 `0x289FC9`、`0x28A109`、`0x28A3E8`。整数乘加是32位，公式采用未溢出的正常游戏数值范围；不能把它当无限精度数学或用四舍五入替代。浮点异常/越界转换不在本次正常数值模型内。

这些函数已经证明参数消费与末端截断；**没有证明完整实战伤害公式**。所示路径没有把目标防御、命中/暴击判定、PVP攻防修正、护盾、减伤等全部接入。也没有证据允许给它补上常见版本的经验上限。

`pvp_damage_ratio`、`pvp_remain_time_ratio` 目前仍停在资源证据层。针对已定位名称的直接引用搜索尚未接到原生消费端；间接表引用、其他模块或受保护代码仍可能存在。搜索无结果不等于字段无效，更不等于证明服务器唯一计算位置。

### 6. 当前能用于理解玩法的结论与不能承诺的结论

1. 技能距离说明确实从效果参数计算，至少不是只在中文文本中写死的数字；方向与实际执行还要追另一条链。
2. 属性有接收、缓存、组件和快照的多层表示；这已经足以解释为什么简单数值扫描可能找错层，但不足以证明攻速使用了某种加密。
3. 技能提示伤害会组合效果参数、状态快照字段和模板端点，并在末端截断。实际打人伤害不能直接照搬提示公式。
4. 客户端既计算一部分射程，也处理收到的距离/障碍失败原因。两者应分开分析，不能把本地距离值视为服务器许可。
5. 强化仍维持第四课结论：已恢复客户端显示概率；神石仍主要是资源与说明对照。服务器随机源、最终成功率和判定顺序尚无证据。

还缺的关键证据有明确位置：RandomMoveLoc执行消费者对reserved3的解释；最终攻速/移速字段的写入与动作调度读取；PVP字段解析后到实际结算的完整使用链；服务器最终判定或同版本正常玩法样本。当前客户端静态文件不能保证这些信息全都存在，本报告不以“全部搞懂”作为无证据的完成声明。

未来若有正常玩法战斗记录，按装备、技能、目标与阶段分层；强化/神石样本同时记录成功数与总次数、条件变化。有限样本报告置信区间并注明模型条件，一次成功或失败不证明概率，也无需为本报告额外消耗材料。

### 两个已经读到的差异，说明为什么不能直接套用

`RandomMoveLocEffect` 使用字符串FRONT/BACK和整数value计算位置，再经DashParam与World.updatePosition更新位置。它给出了可读的执行逻辑，但没有证明当前客户端reserved3的1/2恰好映射这两个字符串。

此提交的BACK分支中，lastSee和lastNonSee初始为0，lastSee后续未被赋新值；循环条件初始不成立，末尾又以lastSee=0计算XY。这会覆盖前面计算的向后目的坐标，属于可见的实现问题。不能把有问题的模拟器分支解释成官方位移规则。

同时提取此服务端技能XML中的5条对应记录：1424为30/FRONT，1463为15/BACK，1544、1545、2278均为10/FRONT。五条value都与当前客户端的reserved2吻合，方向标签也与reserved3=1/2的资源候选一致。这增强了方向映射假设，但属于跨版本资源对照，还不能替代当前客户端执行消费者的代码证据。

强化入口 `EnchantService.enchantItem` 在服务端代码中调用Rnd并决定成功/失败：初始success=50，按石等级/装备等级/品质差增加，辅助剂另加配置值，随后封顶95，用 `Rnd.get(0,100) < success` 判定。Rnd的范围计算含max-min+1；若把101个整数结果视为均匀，封顶对应95/101，不能简单写成95%。这是**此模拟器**的判定代码，与第四课当前客户端提示公式明显不能直接等同。

这份源码使“判定端怎么写”成为可以阅读、复现和比较的问题；它仍不能证明正在玩的经典服后台恰好运行这份代码。后续应先建立版本对应关系，再把其结论接到当前二进制证据里。

当前客户端 `0x6A0B0` 路径在 `0x6A15E` 读取全局状态缓存+0x68（RVA 0xD71BE0），加上角色组件+0x1C88，与调用受保护函数0x1244AE3所得的计时候选比较；若当前值不大于两者之和则退出该路径。后续路径会构造请求、调用传输相关函数，并在 `0x6A350` 将本次计时值写回组件+0x1C88。另有0x5D140的时间补偿和0x14F92的动作检查使用同一个uint16。

### 二、最终角色属性不是单一物品偏移：重算、读取消费和同步是三层

主要调用关系：

```text
装备/技能修正器
  → CreatureGameStats.addModifiers 或 endEffect
  → PlayerGameStats.recomputeStats
  → resetStats → 分类/排序修正器 → applyModifiers → applyLimits
  → getCurrentStat 供攻击/伤害/技能使用
  → SM_STATS_INFO 发给本人，速度变化另广播 SM_EMOTION
  → 当前客户端 S_STATUS → 0x42DD90 → 状态缓存
  → 攻击门槛、射程检查、提示显示等各自消费
```

服务端 `Stat.java:50–104` 区分 origin、base、bonus、old：reset保存旧的base+bonus，将base恢复为origin、bonus清零；最终current=base+bonus。注意 `increase(amount,false)` 的真实行为是**替换base**，不是累加。AddModifier非bonus先算base+value再交回替换；只看方法名字会把基础值重复相加。

`CreatureGameStats.java:159–165、306–310、353–372` 表明增加/移除修正器都会重算；依 HIGH → MEDIUM → LOW 次序应用。Set在HIGH、Add在MEDIUM、Rate在LOW，同一优先级还受修正器ID/收集顺序影响。

`StatupEffect`、`StatdownEffect` 自身是空子类，真正逻辑在 `BufEffect.java:111–183`：读取change列表，值为value+delta×技能等级；ADD建立AddModifier，PERCENT建立RateModifier，REPLACE建立SetModifier。技能名或效果类名本身不决定正负，必须读参数和修正器。

这里有一处容易误读：BufEffect的REPLACE传入bonus=true，而共享applyModifiers会调用Stat.increase增加bonus。因此不能把XML里的REPLACE简单翻译成“最后一次把整个角色属性替换为这个值”；需要看消费实现。本节不将所有同名Buff概括为统一的覆盖或叠加规则。

RateModifier的bonus百分比是 `Math.round(value * baseStat / 100f)`，参考**base**而不是已经加入bonus的current。因而在这一修正器路径里，多项百分比通常分别算出增量后相加，不是自动连续相乘。若更早的非bonus修正器改变了base，百分比参考值也随之改变。整数乘法先发生，后除float；普通有限值的示例不覆盖整数溢出。

`PlayerGameStats.java:245–270` 先发送SM_STATS_INFO，再清空无副手时部分副手字段，顺序也值得保留。单次状态包、服务端重算状态和客户端某次快照不必然完全等价。

对照客户端：此前已确认物品的attackDelay编号29和物品实例+1C8/+1CC是物品修正表示；玩家状态缓存D71B78起始的一块来自收到的S_STATUS。这两条链不能用相同属性名字合并为一个“玩家基础偏移”。

### 三、攻击速度：单位是间隔毫秒，值越小越快

源代码中ATTACK_SPEED用于与System.currentTimeMillis的差比较，因此在此服务端模型中是毫秒间隔，而非“每秒攻击次数”。`PlayerController.java:854–865` 的接收门槛以及 `CreatureController.java:307–317` 的攻击门槛都读取重算后的current值，两者分别保存自己的lastAttackMilis，并非同一个计时字段。

`CM_ATTACK.java:56–81` 请求负载只有目标ID(D)、攻击编号(C)、time(H)、type(C)，没有客户端声明的最终攻击力、伤害或攻速。它先通过PlayerController的时间检查，再查目标并调用attackTarget。请求中的time另外用于广播和延迟扣血，不是给服务端提供“认可的攻击间隔”。

双持算法在 `PlayerGameStats.java:165–228`：

1. 主手基础间隔全额计入；副手基础间隔先乘0.25并Math.round，然后计入。
2. 双持武器的bonus攻速修正器暂存；比较SimpleModifier的value，只选数值较小的一个。对于负数间隔缩减，较小表示更强。这里不是比较两个武器的最终攻击频率。
3. 其他符合路径的修正器继续按优先级应用；百分比bonus参考当时的base。
4. `CreatureGameStats.java:247–278` 先把攻击间隔保底为600；`PlayerGameStats.java:314–318` 再限制负bonus最多缩减基础间隔的一半。

对正的常规基础间隔B，最终下限可写为 `max(600, ceil(B/2))`；完整结果还取决于原始重算值。Java的Math.round(-700.5f)为-700，所以B=1401时半间隔下限是701，不能向下写700。没有在此路径发现“减速后的最大间隔上限”。

| 示例，假设只有列出的武器加成 | 基础间隔B | 未限幅结果 | 最终间隔 |
|---|---:|---:|---:|
| 单手1400，百分比修正-19 | 1400 | 1134 | 1134毫秒 |
| 主手1400、副手1200；武器修正-19和-17 | 1700 | 1377 | 1377毫秒，取-19 |
| 基础2000，百分比修正-70 | 2000 | 600 | 1000毫秒，半间隔限制生效 |
| 基础1401，百分比修正-70 | 1401 | 420 | 701毫秒 |
| 基础1000，百分比修正-70 | 1000 | 300 | 600毫秒，600保底生效 |

对照当前客户端：状态块+68的uint16位于Game.dll **RVA D71BE0**；`0x6A15E` 读它，加角色组件+1C88，再与受保护函数0x1244AE3返回的计时候选比较；`0x6A350` 更新组件时间戳。客户端此分支在now≤sum时退出，服务端在elapsed<interval时退出，等号行为也没有强行写成相同。当前客户端保护计时函数、整数回绕处理和其他攻击路径尚未全部解析。

服务端状态包相同前段位置明确命名ATTACK_SPEED；HP、MP、射程等多个字段也对齐，8,003件武器间隔相同又增加了语义对应的可信度。现在较强的解释是：**模板基础值、属性重算值、收到的缓存、上次动作时间、动作持续时间共同构成攻速行为**。目前没有证据支持“最终攻速必然只藏在一个加密数值中”；也不能因找到缓存就宣布保护表示已经全部解开。

### 四、移动速度、射程和瞬移：数值产生与位置生效分开看

此源码的玩家SPEED先保底600再封顶12000，FLY_SPEED先保底600再封顶16000。`SM_EMOTION.java:82–95、285–290` 按是否飞行选speed，再除1000f发float，同时特定情绪类型带基础/当前攻击间隔。对应的运行/飞行速度范围为0.6–12、0.6–16个坐标单位/秒；其米制解释沿用源码语义，当前客户端最终移速字段仍待追消费链，不能把这两个上限直接写到本机客户端偏移表里。

技能首目标射程在 `FirstTargetRangeProperty.java:52–96`：普通目标R=value，加武器范围时再加ATTACK_RANGE/1000f，随后加3.0容差；MathUtil要求同地图/实例且 `dx²+dy²+dz² < R²`，再做GeoEngine视线检查。坐标点技能分支另用distance≤value，没有同一套武器加成/3.0容差。AOE选目标的TargetRangeProperty另有1.5f容差，不是所有技能统一加3。

当前客户端 `0x19B20` 读取技能+724、+72C，以及同步状态的float D71BDC；也有组合技能距离与武器范围的行为。但本地路径中的1.0距离修正及flag语义，不等价于服务端的3.0或AOE的1.5。提示射程、客户端允许发起、服务端允许命中需要分别验证。

RandomMoveLoc的FRONT分支：按朝向计算 `(x + d*cosθ, y + d*sinθ, z+2)`，写DashParam，然后applyEffect调用World.updatePosition；该World方法写坐标、变更区域并按参数更新已知列表。BACK分支的lastSee始终为0、初始循环不执行，末尾覆盖XY为原XY，属于本提交的明确实现缺陷；初步几何意图与最终执行结果必须分列。

当前客户端提示路径 `0x28B960 → 0x28C468 → 0x28A420` 只消费reserved1/2的距离表达式；reserved3=1/2与五条服务端FRONT/BACK对应，是方向候选的资源证据，仍不是当前客户端执行方向的反汇编证据。

CM_MOVE读取客户端位置/方向，调用World.updatePosition并广播SM_MOVE，另有滑翔、坠落等处理。这解释了普通移动、技能位移和服务端通知是不同入口。此老模拟器的几何校验覆盖不能作为当前线上服务器的校验能力证明；视频里看见位移也不足以区分技能、位置插值、不同步或后台认可。本节没有生成移动修改或发包方案。

### 五、PVP伤害：已找到实际消费端，不能把所有比例合成一个乘数

以下R表示Java Math.round(float)，T表示向零截断；保留各步取整。说明的是这份源码的对应分支，不是未经验证的经典服最终公式。

**物理普通攻击，玩家、有武器：**

```text
W = 在 MAIN_MIN_DAMAGES..MAIN_MAX_DAMAGES 间抽整数（含两端）
D0 = R(W * POWER * 0.01f) + MAIN_HAND_PHYSICAL_ATTACK的bonus
     + skillDamages + bonusDamages [+ 当前路径的主手力量碎片加值]
D1 = max(1, D0 - R(目标PHYSICAL_DEFENSE * 0.10f))
```

入口为StatFunctions.java:276–363；普通攻击传skillDamages=bonusDamages=0。有正skillDamages的技能会比较两手武器均值，可能取副手的min/max；比较本身用整数除法。徒手和召唤物/NPC是独立分支，不能套这条。

AttackUtil.java:56–129后续顺序：判闪避/招架/盾防 → 相应减伤 → 独立判暴击与武器暴击倍率 → R(观察者物理倍率) → adjustDamages → 未命中清零/非未命中至少1 → 生成多段 → 护盾检查。盾防为 `D - trunc0(D*DAMAGE_REDUCE/100)`，因为源码整数相除后才调用Math.round；招架为T(D×0.6)，不能把这两步统一成四舍五入。

武器暴击倍率：匕首2.3，单手剑2.2，钉锤2.0，大剑/枪戟1.8，法杖/弓1.7，其余分支1.5；先R(D×倍率)，再R(D−D×PHYSICAL_CRITICAL_DAMAGE_REDUCE/1000f)。普通物理攻击的splitDamage并不是把总伤害拆分：首段D，后续每段R(D×0.1f)，因此N段未被护盾调整前合计为 `D+(N−1)*R(D*0.1f)`。多段包也不代表神石逐段抽签。

**技能专用PVP倍率在更早的阶段：**

DamageEffect.java:75–106先生成技能值，包括value+delta×技能等级以及value2/delta2的武器均值修正。只有目标Player且pvp_damage≠0时，将这个技能值乘pvp_damage/100f并R，然后把它交给物理或魔法伤害函数。bonusDamage是另一参数，在这一步不一同乘倍率。字段缺省0表示跳过该修正，不是“PVP零伤害”。DelayDamageEffect也有同样的早期消费。

这回答了倍率120/130怎么用：它们在已追到的这两类效果中调节**技能项**，不是把武器基础、bonusDamage和结算后的所有伤害统一提高20%/30%。其他效果家族仍需看自己的消费端。

**共同PVP修正 adjustDamages，AttackUtil.java:651–713：**

```text
D2 = R(D * 0.60f)
a = 攻击者PVP_ATTACK_RATIO * 0.001f
b = 目标PVP_DEFEND_RATIO * 0.001f
D3 = R(D2 * (1 + a - b))
```

适用攻击者Summon/Player/NpcWithCreator、目标Player/Summon的该分支。注释说50%，实际代码60%；装备PVP攻防比例是在同一括号里相减，**不是(1+a)*(1-b)**。这一步函数内未见该比例的单独上下限，后续攻击分支对非未命中结果设至少1；不能把它解释为全局没有限制。

若双方actingCreature是Player且种族不同，还按Influence比例选择1.2、1.15或1.1，然后用int复合赋值向零截断；满足后面的自定义等级配置时再执行等级修正。配置 `gameserver.dmgreduction.lvldiffpvp` 注解默认false。其diff=3..14的代码是 `baseDamages -= diff*0.04f`，并非乘(1−diff×4%)：例如正伤害660减0.12f后截断为659。diff≥15才乘0.4并截断。此处很可能存在作者意图与实现差异，但本节只把实际行为当事实。

例如进入共同PVP修正前D=1000，a=0.2、b=0.1，则先600，再660；若错误地相乘，会算648。种族祝福、技能前段倍率、暴击、盾防、观察者及护盾还会改变这个例子，因此不能用660代表所有对战情景。

**魔法伤害需区分普通魔法攻击与技能：**

- 普通魔法攻击：R(随机武器值×KNOWLEDGE×0.01f)+MAGICAL_ATTACK bonus，再R(D×(1−元素防御/1000f))，至少1；此函数不使用BOOST_MAGICAL_SKILL。
- 魔法技能：StatFunctions.java:480–505计算 `R(baseDamages*(K/100f + BOOST_MAGICAL_SKILL/1000f)) + bonusDamages`，再乘元素防御并R、至少1。实际被调用形参dot=true时K=100，false才读取KNOWLEDGE。调用方将变量命名applyKnowledge，但不能按这个名字反推布尔语义；DamageEffect默认调用传true。
- 魔法暴击先执行int的 `D *= 1.5f`（向零截断），再R暴击减伤；随后PVP/等级adjust，再R观察者魔法倍率，与物理普通攻击的顺序不同。
- 普通魔法攻击的calculateMagicalStatus竟调用**物理暴击率**函数；魔法技能用calculateMagicalCriticalRate。这是此提交的一处可见行为差异，不能套用“魔法均由魔法暴击决定”的简化结论。

玩家魔增在重算时上限2600；元素抗性下限-90，但伤害函数与重算函数不是同一个边界。魔法抵抗值MAGICAL_RESIST用于命中概率，元素抗性用于伤害倍率，二者不是一个“魔防”。

**真正扣血在服务端：** CreatureController累加AttackResult并广播SM_ATTACK；time=0立即调用目标onAttack，否则调度延后；onAttack经过施法打断、观察者、仇恨和伤害通知，最后调用LifeStats.reduceHp。DamageEffect则把计算值放reserved1，applyEffect再调用onAttack。护盾/反射等也会修改AttackResult，完整公式必须带分支，不能只截到adjustDamages就声称是最终扣血。

对照当前客户端：此前还原的物理/魔法公式位于提示格式化函数，末端是CVTTSS2SI向零截断；服务端主要使用Math.round，且多处显式/复合赋值截断。提示公式中POWER变化的系数也不能与服务端随机基础攻击的POWER×0.01直接等同。客户端收到的S_ATTACK会建立动作队列，收到攻击结果会选择“距离过远/过近/障碍”等提示，它们支持“表现/接收”职责，尚未证明本机还完整执行了上述PVP扣血公式。

### 六、命中、暴击与防御阈值：先分属性差，再分抽签与顺序

以下省略强制状态覆盖，整数除法均向零截断。双持时部分命中/暴击值先取两手整数均值，即使外面写Math.round，也不能恢复被整数除法截掉的0.5。

| 源码分支 | 计算出的判定阈值 | 取值限制 |
|---|---|---|
| 闪避 | (目标EVASION−攻击命中−技能accMod)/10 | ≤0返回1，上限30 |
| 招架 | (目标PARRY−攻击命中)/10 | ≤0返回1，上限40；普攻需目标持武器 |
| 盾防 | (目标BLOCK−攻击命中)/10 | ≤0返回1，上限50；普攻需目标持盾 |
| 魔法抵抗 | (MAGICAL_RESIST−MAGICAL_ACCURACY−accMod)/10；目标高超过2级再加(级差−2)×10 | 下限0，上限95 |
| 物理暴击净值C | R(双持均值或主手暴击×criticalProb−目标物理暴击抵抗) | 再进入下述分段 |
| 魔法暴击净值C | R(魔法暴击×criticalProb−目标魔法暴击抵抗) | 同样分段 |

暴击阈值r(C)：C≤440为C×0.1f；440<C≤600为44+(C−440)×0.05f；C>600为52+(C−600)×0.02f；r最低1。这一函数没写最高概率限制，但抽签结果本身有限。

关键是消费者多用 `Rnd.get(0,100) < r`，随机集合为0..100，共101个整数。整数阈值r对应r/101；非整数对应满足条件的整数个数/101，等效为裁剪后的ceil(r)/101。不是把r除100，也不是每点属性都平滑增加概率。源码中的float32舍入会影响恰好靠近整数的阈值，应保留计算顺序。

| 净暴击C | 阈值r约值 | 通过抽签的整数个数 | 概率（均匀假设） |
|---:|---:|---:|---:|
| 400 | 40 | 40/101 | 39.6040% |
| 440 | 44 | 44/101 | 43.5644% |
| 441 | 44.05 | 45/101 | 44.5545% |
| 450 | 44.5 | 45/101 | 44.5545% |
| 600 | 52 | 52/101 | 51.4851% |
| 601 | 52.02 | 53/101 | 52.4752% |
| 700 | 54 | 54/101 | 53.4653% |

440/600是**扣除抵抗、乘criticalProb后的净值拐点**，不是任何目标都通用的面板“毕业值”。小数阈值与整数抽签使同一小区间可能没有实际概率增益；不同目标的抵抗又会移动区间。这是这份模型对配装有用的地方。

普通物理攻击先独立抽闪避，未闪避再抽招架，未招架再抽盾防。设各自抽签概率d/p/b，则实际闪避d、招架(1−d)p、盾防(1−d)(1−p)b；不能把三个阈值直接相加。三个阈值都封顶、目标持武器/盾、无强制状态时，实际约为29.7030%闪避、27.8404%招架、21.0181%盾防、21.4385%正常命中状态；暴击随后可与招架/盾防组合。盾防发生率与盾防减伤百分比是两个不同属性。

物理技能在AttackUtil的状态函数里没有闪避检查，不代表技能不能闪避：EffectTemplate.java:311–329在共用成功效果路径另抽闪避/魔抗，noresist可跳过；异常抵抗、条件效果、前置效果也会阻止执行。因此技能命中概率不能仅从calculateSkillPhysicalStatus推导。

源码返回阈值100的“总是闪避/暴击”路径如果仍经过0..100的严格小于抽签，只能100/101；不要把注释或观察者名称当作100%必然成功。其他直接跳过抽签的路径需另审。

### 七、神石：第二参数在这份源码中参与一次随机阈值，不能只读提示百分比

`GodStone.java:76–110` 装备时安装ATTACK观察者，卸下移除。每次attack回调：

```text
p = probability，L = probabilityleft（Java缺省0）
T = Rnd.get(p-L, p)                      # 两端都含
若是双持副手神石：T = trunc0(T * 0.5)
U = Rnd.get(0,1000)                      # 1001种整数结果
若 T > U：尝试神石技能 → canUseSkill/目标条件 → Effect初始化/应用
```

若0≤L≤p≤1000且整数均匀，主手通过随机分支的概率为 `(p−L/2)/1001`。副手必须对每个T取floor(T/2)后求均值再除1001，奇数阈值使它不一定恰好是主手的一半。两层随机数和后续效果抵抗都在源码的服务端路径，客户端对应参数是资源/提示数据，未证明它能决定结果。

例如物品168000034两边都有p=60、L=30。此模拟器T在30..60抽，平均45，随机分支概率45/1001≈4.4955%；只用p/10会显示6%。副手该区间的平均截断阈值为690/31，随机分支约2.2236%。物品168000028两边p=40且第二参数缺省，在此模拟器随机分支是40/1001≈3.9960%。这些只说明源码实现，不证明经典服正式概率；资源是否正式可用也另查。

普通攻击通知神石观察者在CreatureController.java:362–373：闪避/抵抗跳过，其余状态通知。多段攻击先累加结果，再一次notifyAttackObservers；并非splitDamage的每一段都抽一遍。DamageEffect/DelayDamageEffect也有通知入口，能否触发还取决于成功效果链和技能限制。本轮没有把所有技能、持续伤害及反射归为相同触发频率。

即使随机分支通过，仍可能因canUseSkill、当前目标或Effect抵抗未产生可见效果；弹出发动消息也在部分后续检查之前。因而战斗日志“最终看见的神石效果次数/攻击次数”不等同于单独的T>U概率。

### 八、强化：服务端判定、持久状态写回与客户端概率提示已明确分开

`EnchantService.enchantItem:119–280` 的成功阈值：

```text
Q = COMMON/JUNK:0；RARE:5；LEGEND/MYTHIC:10；EPIC/UNIQUE:15
S = 50 + 5*max(石等级−装备等级−Q, 0) + 辅助剂加值
S = min(S,95)
成功 = Rnd.get(0,100) < S
```

前置条件包括目标可强化、石等级不低于装备等级；此方法先消耗强化石，再按条件消耗辅助剂。辅助剂默认加10，三个配置注解默认10/15/20；真正启动时配置可覆盖。目标强化等级超过10会增加辅助剂消耗，但**这个方法的成功率没有因+11..+15单独减半**。

如果成功：UNIQUE/EPIC最高15，其他最高10；失败：当前>10回到10，当前1..10减1，0不再减。随后必要时卸下旧属性修正、setEnchantLevel、重新应用属性，发送SM_UPDATE_ITEM，并标记装备/背包UPDATE_REQUIRED，再发送成功/失败消息。持久状态标记已确认，数据库最终落盘调度不是本节已完整审计的范围。

| S阈值 | 真实通过整数个数 | 模型概率（均匀假设） |
|---:|---:|---:|
| 50 | 50/101 | 49.5050% |
| 60 | 60/101 | 59.4059% |
| 80 | 80/101 | 79.2079% |
| 95，封顶 | 95/101 | 94.0594% |

以品质Q=15、石比装备高20级为例：无辅助剂S=75，加默认普通辅助剂15为S=90；高25级时基础达到100后封顶95。以上是输入分层示例，不是建议为核验额外购买或消耗材料。

当前客户端 `0x316610` 已还原的UI公式使用品质系数60/40/30/20/15/10；+1..+10基础封顶800，+11..+20先除2再封顶500，辅助剂后总值封顶1000，显示乘0.1。它与本服务端的品质减项、封顶95和不区分高阶基础概率的实现明显不同。对比揭示“提示概率≠源码判定概率”，不能选一个更好看的数当线上真实概率。

### 九、这轮结论对PVP和强化学习的具体帮助

1. 攻速配装要看主副手基础间隔、武器加成选择、其他修正器和下限。达到某条间隔下限后，同路径再堆加速没有继续减少间隔的收益；它仍可能改变其他动作或技能，需逐条看消费端。
2. 命中能同时改变闪避、招架、盾防差值，但这些状态依序排斥；盾防概率与盾防减伤分别评估。暴击要减目标抵抗后看440/600拐点与整数抽签，不使用固定面板阈值。
3. PVP倍率要分技能项、装备攻防项、种族祝福、等级配置、暴击及护盾。源码可以建立明确模型和装备比较假设，正常玩法的同装备/技能/目标/阶段日志才能核对当前版本。
4. 神石要记录主副手、第二参数、实际通知次数与效果抵抗；强化要记录品质、石装等级差、辅助剂配置与强化阶段。一次成功或失败没有证明概率的能力；有限样本只能给分层估计/置信区间。

已完成的主要源码链不再是待定。仍待追的是当前客户端RandomMoveLoc方向执行、最终移速同步消费者、保护计时函数、当前版本PVP参数消费，以及源码尚未逐家族审计的护盾/吸收/反射/治疗/异常抵抗/召唤物路径。后续可沿这些具体入口继续，不必为了本节结论附加正在游玩的客户端。

### 1. 当前客户端移速：收到的值、派生值和本地缓存已分开

REA 对路由器 `RVA 0x426F70` 的反编译确认：内部消息编号 **37（0x25）** 调用 `0x430410`；旧注册表证据将此编号命名为 `S_ACTION`。这与内部编号 36 的 `S_ATTACK` 不同，也不是未经证明的线上网络 opcode。

`0x430410` 将消息对象的 `+18` 数据基址和 `+20` 偏移组成 payload 指针，然后读取：

| payload 相对位置 | 表示 | 证据与用途 |
|---|---|---|
| +0 | 对象编号 u32 | 用于查找对象与组件 |
| +4 | action 字节 | 选择动作分支 |
| +5 | 状态 u16 | 进入动作/状态更新 |
| +7 | float | `0x430457` 读入 XMM9，随后传给速度分发函数 |
| +B / +D | 两个 u16，仅 action=35 分支 | `0x430710/717` 写入组件 +508/+50A |

速度链的关键位置：

```text
消息37 → 430410
  → 430BFA / 4304D8 → 4EB620
  → 4BF7A0 查找组件
  → 4EB694：组件虚表 +248
  → 460440：速度设置函数
```

REA 指令明确显示 XMM2 中的 float 被分发函数保存，再放到 XMM1 交给虚表函数。此处 Hex-Rays 自动推导的分发函数原型漏掉了浮点参数，所以不能只靠其两参数伪代码否认速度传递；判断以调用点和寄存器指令为准。

`0x460440` 的核心计算（s 为收到的 float）：

| 组件相对字段 | 静态确定的内容 | 分类 |
|---|---|---|
| +38 | s | 收到值的镜像 |
| +6C8 | s | 速度值及后续消费者读取来源 |
| +6CC | float32(s×s) | 本地派生的平方值 |
| +6D0 | 通常为 float32(1/s)；接近零时为 1 | 本地派生的倒数/特殊值 |
| RVA D71CA0 的全局 float | 仅对象身份匹配本地玩家时写入 s | 有条件的本地玩家缓存 |

接近零分支用正负约 `0.0001` 比较；这里描述有限数值常见输入，未把 NaN/Infinity 边界当作正常玩法规则。设置函数还重置组件状态、更新动画和本地变化位。当前已读函数中没有看到服务器参考模型的地面 12/飞行 16 上限判定，**不等于整个客户端没有上限**。

旧 PE/RTTI 辅助证据显示 +248 槽在 CharacterObject、Player、AIObject、AIToyPet、RopeObject 的表中都指向该函数。因此它是多类对象共享的设置路径，不能只凭函数地址把所有入参认作玩家。REA 当前数据库的 incoming xrefs 没有列出原始文件里的每个虚表指针；已用原始 PE qword 核对 Player 表对应位置仍指向 `0x180460440`。这说明“IDA 没有列出引用”不等于“原始字节没有引用”。

**结论更新：当前客户端最终移速同步消费者已找到一条实证链；组件内同时有收到值、平方、倒数和本地玩家全局缓存。** 这不是已定位运行时对象地址，也没有证明在服务器上修改移动规则。全局 D71CA0 位于旧 S_STATUS 同步块范围之外，不能把它误写成该块里的直接速度字段。

### 2. 攻速隐藏计算：同步的两个间隔进入动画比值

REA 对 `0x4BC390` 的反汇编、反编译及完整 dossier 均成功。速度设置函数在 `0x4604F5/51D` 调用它更新两路动画。该函数按动画名称和模型选择倍率：

- 移动动画分支在 `0x4BC4CB` 读取组件 +6C8，再除以模型动画参考速度，部分模型还有第二个比例因子。
- 动画名称匹配 `cattack` 的分支，在 `0x4BC5B9/C9` 读取组件 **+508 / +50A 的 u16**，二者非零时于 `0x4BC5ED` 做 **前者/后者**，最终再乘组件 +4F4 的全局动画比例。
- 其他 fire/cast 分支也存在间隔比、条件修正和上下界相关处理，尚未把其所有模型输入和 +1188/+118C 字段业务意义审完。

以 `cattack` 分支为例，令 B=组件+508，C=组件+50A，G=组件+4F4：

```text
B、C 均非零时：动画倍率 = float32(float32(B/C) × G)
任一为零时：此分支回退到 1，再乘 G
```

例如 B=2000、C=1000、G=1，倍率为 2；它证明动画播放比例的计算，不能单独证明服务器每秒允许两倍攻击次数。第六课已确认的攻击请求时间门槛是另一条读取链。

### 3. 保护计时、PVP 参数和位移：本轮实测到了哪里

### 4. 辅助参考源码：护盾、吸收、反射与保护转移

以下公式仅针对固定 AionLightning 提交 `94fc8048e5fc198f000c0ca2176c65034c57cb39`；不是当前经典服后台事实。定位见 `analysis-summary.json` 的源码行号摘录和 Git blob 校验。覆盖主要消费者，未声称穷尽整个技能模板、所有扩展效果和配置。

`ObserveController.java:340` 按攻击计算观察者的加入顺序调用 `AttackShieldObserver.checkShield`，传入可被前一个观察者改写的伤害列表。观察者再逐个 AttackResult 处理；DODGE/RESIST 项被跳过。**判定单位是伤害段，不是默认每次按键一次。**

护盾有效性抽样为 `Rnd.get(0,100) <= probability`。在概率参数 p∈[0,100] 时，实际比例为 `(p+1)/101`：p=0 仍为 1/101，p=50 为 51/101，p=100 为必然通过。先经过攻击类型过滤、再抽样，不能无条件把此比例当作所有伤害的触发率。

| 家族 | 核心消费者 | 固定源码行为 |
|---|---|---|
| 普通护盾 | AttackShieldObserver:91–108 | 百分比：先算 int(D×hit/100)；固定值：min(D,hit)；再按剩余总预算 value 截断，减少该段伤害和预算 |
| 反射 | 同文件:112–126 | 距离通过后固定反伤 hit，直接调用攻击者 onAttack；原段伤害不因此减少，不按原段伤害乘百分比 |
| 保护/转移 | 同文件:128–152 | 百分比：int(D×value×0.01)；固定值：value；受保护者伤害降到最低 0，保护者收到转移值 |

普通护盾预算耗尽后，该观察者直接 return，当前列表的后续段不再由它处理。例如伤害段 [500,300,200]，每段最多吸收 250，总预算 400，结果为 [250,150,200]；总共吸收 400。反射同理按每个符合条件的伤害段触发固定额外伤害，而不是消耗普通盾的总吸收池。

源码中发现三个需要保留的实现问题：

1. 攻击类型 MAGICAL_SKILL 分支缺少 break，先排除 PHYSICAL，再落入 PHYSICAL_SKILL 分支排除 MAGICAL；对这两种普通 damageType 都无法执行护盾。AttackResult 默认构造为 PHYSICAL，不能忽略这个过滤缺陷。
2. ShieldEffect 注释说反射也只能有一层，但实际比较 `et.getClass()==this.getClass()`，按完全相同类处理，不能据注释宣称所有护盾/反射互斥。
3. 固定转移值没有先取 min(D,value)。例如原伤害 100、固定转移 200，受保护者为 0，保护者仍进入 200 的 onAttack 请求；这不是守恒的伤害分配。

普通盾总预算、每段限额按 value/delta 和 hitvalue/hitdelta 随技能等级计算；反射使用 hitvalue 系列作反伤；ProtectEffect 在已读 startEffect 中使用原始 value，未采用相同的 value+delta×level。StoneSkin 的 UD 扩展列表为空、添加代码被注释，不能写成已有的抗击倒加成。

PVP 学习上的帮助：看日志时应保留每段伤害、观察者顺序、盾类型、剩余预算和距离条件。一个总伤害数字不能反推每段吸收，也不能证明统一反伤百分比。反射/转移这里直接进入 onAttack，没有重新走同一段 AttackUtil→checkShield 路径；未据此扩展成“所有回调永不再次触发”的全局结论。

### 5. 辅助参考源码：治疗、持续治疗和吸血

`AbstractHealEffect.java:51–98` 中 V=value+delta×技能等级。常规正数范围下：

```text
百分比治疗：possible = 整数向零截断(maxHP × V / 100)
固定治疗（允许加成且施法者为玩家）：
  possible = int(float32(V × (施法者 healRate + (施法者 BOOST_HEAL−100)/1000)))
其他固定治疗：possible = V
初步实际值 = min(maxHP−当前HP, possible)
HP治疗遇到受治疗者 DISEASE：0
```

百分比路径没有使用 BOOST_HEAL。固定治疗用的是 **施法者** 的 healRate 和治疗增幅，不是受治疗者的值。DeboostHealEffect 修改中效果角色自身 controller.healRate，所以“给目标挂减疗就一定降低任何第三方对它的治疗”不成立于这条代码；病症 DISEASE 则在目标生命值 increaseHp 的公共消费者中再次阻止回复。此处仅报告源码行为差异，未断言线上机制。

持续治疗在 calculate 阶段算好 hot/mot 并保存；每次 tick 再取目标当前缺损量、最大值和 DISEASE 状态。由此支持：施法者加成取计算时快照，而目标的缺血上限与禁疗检查在 tick 时再次判断。没有把即时治疗和持续治疗的所有分支合成一个公式。

物理/魔法即时吸血使用保存的伤害 reserved1×百分比/100；持续魔法吸血使用 reserved4。它们没有从目标最终 HP 减少量重新读取实际损血。过量击杀、其他生命值处理和加血上限因此会让“显示伤害×吸血率”与最终回复不同。increaseHp 最终裁到最大 HP，但调用 onIncreaseHp 时传入的是原请求 value，日志值也不能未经核对就当作真实 HP 差值。

本轮未补出反治疗、所有触发型治疗和所有回血道具的完整共同模型；OneTimeBoostHeal/HealCastorOnAttacked 等仍需要单独逐路径审计。

### 6. 辅助参考源码：异常抵抗的整数门槛

`EffectTemplate.java:493–629` 的异常状态概率分支，先取 effectPower=1000，按效果的抵抗类型减抗、按特定攻击者属性加成，某些控制效果还受 boss/ALLRESIST 直接拒绝。BLEED/POISON 没有照搬这些控制组检查。Stun/Stumble/Stagger 各自传入对应抵抗枚举。

目标等级高于施法者时，代码为：

```java
effectPower -= effectPower * (differ / 10);
success = Rnd.get(0, 1000) < effectPower;
```

`differ/10` 是整数除法。对正的 effectPower：等级差 1–9 不在这一步产生惩罚；10–19 变成 0；20 以上可变为负值。它不是每级平滑降低 10%。最后抽样有 1001 个整数结果，power=1000 对应 1000/1001，不是精确 100%；power=900 对应 900/1001。函数没有显式统一 clamp；极端门槛的有效概率由比较式和随机范围决定。

随后 CommonEffectTemplate 还可能做普通闪避/魔法抵抗、条件和前置效果判定。`noresist` 跳过后者普通命中抵抗，并不自动跳过所有异常状态抵抗。被动、ReturnPoint、RandomMoveLoc 存在直接成功的特殊路径。PVP 控制日志应把不同门槛分开，不能仅用魔命−魔抗一个数解释所有成功率。

## 2. 攻击计时：时间基准有额外调整入口

此前已确认 `6A0B0` 用同步全局 `D71BE0` 的 uint16 与组件 `+1C88` 相加，比较保护函数 `1244AE3` 返回值的低32位。本轮发现它在比较前先执行 `5D140`，XMM1 参数为零；这个函数会修改同一个 `+1C88`。

```text
6A0B0
  → 5D140(组件, XMM1=0)：补充本地额度，并按条件调整时间基准
  → 1244AE3：取得仍未识别来源的值 n
  → threshold = u32(组件+1C88 + u16[D71BE0])
  → n <= threshold 时拒绝这一分支（无符号 jbe）
  → 通过后继续构造请求；成功路径写 +1C88 = n
```

这证明“攻击计时不只有一个固定字段读写”的判断有当前版本代码支持。但它没有证明攻击速度被加密藏在某个玩家偏移，也不能把这条本地调整机制当成服务器规则。

### 2.1 补充额度的算术

`5D15D–5D1AC` 使用组件 `+1C98`（uint32）和 `+1C94`（float32）：

```text
Δ = u32(n - [+1C98])
仅 Δ > 5000 时：
  q = floor(Δ / 5000)
  [+1C98] = u32([+1C98] + 5000*q)
  [+1C94] = min(float32(float32(q*0.2f) + [+1C94]), 0.5f)
```

实际常量 0.2 是 float32 的 `0.20000000298023224`。边界是 **大于5000**，恰好5000不补充。乘法高位与右移实现无符号除5000；复核脚本对10个边界和100,000个固定种子样本验证等价，但不声称随机测试穷尽所有uint32输入。

### 2.2 从当前动作记录形成调整量

XMM1 小于约0.001且动作编号 `+AB0` 非零，并且 `+AB4` 属于1031/1028/1027/1029时，函数复制组件 `+8D0` 起的一块数据。局部记录 `+50/+54` 对应源字段 **+920/+924**，这只是按复制布局确认的来源，字段业务名称未知。

令这两项为 a、b，先算 r=b−a。b<=0或 `(b*30)/100 <= r` 时直接返回；否则候选调整量 δ 为 `(b*30)/100−r`。不进入这些条件时，δ 保留输入的XMM1。计算逐步使用float32，不能把未命名字段直接叫作“技能CD”或“攻击前摇”。

### 2.3 更新基准与反编译器的签名错误

当δ>0并满足比较条件时，代码取 `used=min([+1C94],δ)`，扣减额度，并写：

```text
[+1C88] = u32(n + trunc(float32(used*1000.0f)) - u16[D71BE0])
```

比较条件的正常有限数模型为：

```text
float32(float32(δ*1000.0f) + float32(u32(n)))
  > float32(u32([+1C88] + u16[D71BE0]))
```

**必须以指令为准**：`5D169 mov r9d,eax`、`5D301 add eax,[rbx+1C88h]` 均使高32位为零；`5D312 cvtsi2ss xmm0,r9` 与 `5D322 cvtsi2ss xmm0,rax` 转换的是这些非负64位值。伪代码把右侧显示为 `(float)(int)result`，在高位为1的32位时间值上会产生错误模型。因此报告没有采用它的有符号转换。

1000和5000与秒/毫秒转换相容，但保护计时来源、频率和回绕行为仍未知。无符号加法的回绕和浮点精度也意味着这不是对所有时刻成立的连续实数时间公式。NaN、无穷和非法浮点转整数未被本轮算术例子覆盖。

关键原始证据：`attack-consumer-5d2f7-insns.*`、`timestamp-adjustment-decompile.*`、`attack-consumer-6a15e-insns.*`。

## 3. 动画事件参数如何进入攻击请求

`4BC390` 的直接调用者扩展为 `460440/47C940/47CE80/493940`。本轮重点闭合了 `47C940 → 47CC70 → 6A0B0`。

`47C940` 先调用 `4BC390` 取得动画比例R（异常非正路径另有回退），在步长 **0x58** 的事件记录中查类型 **12**，调用 `46B980` 展开事件。展开函数将原记录 **+20** 原样复制到展开记录 **+20**；随后这个位置作为float读取，并除以R。这把“动画事件参数除以比例”从猜测推进为指令证据；事件业务名和单位仍未完整识别。

`47CC70` 将该项与另一项几何/记录相关值相加，后者涉及 `6A8A3F` 数学间接入口及记录字节 `+1E6`。该数学入口指向编码的间接槽，当前没有证据把它正式命名为sqrt；也不能把整个结果无条件叫作纯攻击间隔。

`6A0B0` 调用 `47CC70` 后，执行乘1000、加0.5、`cvttss2si eax,xmm0`，最后写AX到构造中请求缓冲区的 **+0xC**。缓冲区长度字段为15。对于正常非负且整数转换有效的值d，写入值为：

```text
low16(trunc(float32(float32(d*1000.0f) + 0.5f)))
```

示例 d=0.1234→123，d=0.1236→124；d=65.536→低16位为0。后一个仅用来说明字段宽度，**不代表服务器接受、合理攻击周期或当前玩法可以产生这个输入**。内部缓冲区不是已抓包验证的线路协议，更不证明服务器直接信任客户端参数。

现在需要分别讨论：同步间隔、动画比例、事件参数、请求参数、本地时间门槛、服务器结算。它们彼此有调用关系，却不是一个可互换的“攻速值”。

## 4. 移速：初始化、派生写入与消费者

### 4.1 先确认对象家族，排除同偏移误命中

`4B0F00` 构造路径装入 `CharacterObject` 虚表，随后以qword零写 `+6C8`，同时覆盖 `+6CC`；以qword `0x3F800000` 写 `+6D0`，即低float=1，邻接高32位=0。结合第七课设置函数 `460440`，这个对象家族的字段语义为收到/设置的速度s、s²、近零处理后的倒数。

119个候选入口中，133条显式访问分为21条标量浮点访问、10条虚调用槽偏移和102条其他访问。后两类包括别的对象、指针、栈变量或数组；**同为+6C8不代表同一字段**。搜索也不覆盖批量清零、索引化访问和未被IDA识别的代码。

### 4.2 不只有消息写入：关联组件派生传播

`4BF3C0` 经关联表和 `4BF7A0` 取得组件；mask&1时读取源组件 `+6C8`，常规乘约1.1。源 `+2D8` 的bit1设置时改用12；否则源 `+2C0==8` 或 `+2D8` 的bit4设置时改用30。最终调用目标组件虚表 **+248** 的设置接口。

这给出新的本地派生写入入口。源/目标的关联业务类别尚未证明，不能猜填“坐骑”“宠物”；12、30也不是全角色移速上限。反编译器在虚调用中漏掉XMM浮点实参，报告采用 `4BF463–4BF4A2` 的指令序列。

### 4.3 速度平方参与位置差异容差

`4677C0` 比较两个三维坐标的距离平方，与 `float32([+6CC]*0.0004f)` 比较；另有时间差不大于160的允许路径。超过两条条件后设置 `+15C8` 字节并返回不同状态。`0432A0/0213C0` 有同类平方字段使用。

在通常非负有限速度下，其尺度约为 `(s*0.02)^2`，但具体坐标单位、状态用途和完整分支仍需追踪，**不是已证明的反作弊瞬移阈值**。时间来源 `33E6E0` 已追到全局 `D6ADF0` 的虚表+138取得接口，再虚表+10返回浮点结果；没有解析到具体实现或系统API。

`464510` 另一分支比较距离平方与 `float32(float32([+15A0]*s*0.001f)^2)`，同时检查对象ID和状态。这个较大函数有重建/跳过等分支，不能把一个局部分支写成通用角色位置积分公式。

### 4.4 速度限制样式的向量消费者

`4BBA10` 经实体虚表+178取得接口，方法+18填充向量/状态记录。经过数学间接函数取得候选L，在L>约0.01时，用 `min(s,L)/L` 缩放平面向量，再由接口+20消费构造记录。还会按条件调用 `4BF3C0(mask=1)`。

算术形状支持“速度参与向量幅度限制”的推断；数学间接函数、接口真实类型以及这个向量是否最终世界速度尚未知，因此没有填入完整物理运动公式。

### 4.5 倒数消费者已追到向量插值

`4C30CA` 取 `a3=max(0.1f,[+6D0])`，调用 `0B4B80`，传入组件 **+14** 的三项向量及另一三项目标向量。它先比较点积与1的接近程度；未足够接近时，形成：

```text
α = min(1.0f, float32(frameCandidate * (4.6f / max(0.0001f,a3))))
v = current + (target-current)*α   // 每步float32
```

随后对v的平方和调用同一个数学间接入口，并按结果作除法缩放；非正结果使用(0,0,1)回退。这里的4.6实际为float32 `4.599999904632568`。`frameCandidate` 的 `33E680` 也走 `D6ADF0 → 虚表+138 → 接口虚表+28`；单位和实现未确认。

这是一条**方向样式向量的插值/缩放路径**。函数返回变化后，`4C30E6` 调用 `4BE930`，后者继续形成数据并交实体虚表+478消费。已读到提交入口，但实际接口实现仍待定位，不能把它说成已证明的世界坐标更新。0.1是此插值参数的下界，不是已证明的最终角色速度上限。

同样，`4B3640` 中速度大于约5.999的比较只是多条件布尔状态判断，不是“最高移速6”。`493940` 中某些速度读取用于动画日志格式化，不能列作运动执行证据。
