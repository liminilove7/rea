### 二、最终角色属性不是单一物品偏移：重算、读取消费和同步是三层

主要调用关系：

```text
装备/技能修正器
  → CreatureGameStats.addModifiers 或 endEffect
  → PlayerGameStats.recomputeStats
  → resetStats → 分类/排序修正器 → applyModifiers → applyLimits
  → getCurrentStat 供攻击/伤害/技能使用
  → SM_STATS_INFO 发给本人，速度变化另广播 SM_EMOTION
  → 当前客户端 S_STATUS → 0x42DD90 → 状态缓存
  → 攻击门槛、射程检查、提示显示等各自消费
```

服务端 `Stat.java:50–104` 区分 origin、base、bonus、old：reset保存旧的base+bonus，将base恢复为origin、bonus清零；最终current=base+bonus。注意 `increase(amount,false)` 的真实行为是**替换base**，不是累加。AddModifier非bonus先算base+value再交回替换；只看方法名字会把基础值重复相加。

`CreatureGameStats.java:159–165、306–310、353–372` 表明增加/移除修正器都会重算；依 HIGH → MEDIUM → LOW 次序应用。Set在HIGH、Add在MEDIUM、Rate在LOW，同一优先级还受修正器ID/收集顺序影响。

`StatupEffect`、`StatdownEffect` 自身是空子类，真正逻辑在 `BufEffect.java:111–183`：读取change列表，值为value+delta×技能等级；ADD建立AddModifier，PERCENT建立RateModifier，REPLACE建立SetModifier。技能名或效果类名本身不决定正负，必须读参数和修正器。

这里有一处容易误读：BufEffect的REPLACE传入bonus=true，而共享applyModifiers会调用Stat.increase增加bonus。因此不能把XML里的REPLACE简单翻译成“最后一次把整个角色属性替换为这个值”；需要看消费实现。本节不将所有同名Buff概括为统一的覆盖或叠加规则。

RateModifier的bonus百分比是 `Math.round(value * baseStat / 100f)`，参考**base**而不是已经加入bonus的current。因而在这一修正器路径里，多项百分比通常分别算出增量后相加，不是自动连续相乘。若更早的非bonus修正器改变了base，百分比参考值也随之改变。整数乘法先发生，后除float；普通有限值的示例不覆盖整数溢出。

`PlayerGameStats.java:245–270` 先发送SM_STATS_INFO，再清空无副手时部分副手字段，顺序也值得保留。单次状态包、服务端重算状态和客户端某次快照不必然完全等价。

对照客户端：此前已确认物品的attackDelay编号29和物品实例+1C8/+1CC是物品修正表示；玩家状态缓存D71B78起始的一块来自收到的S_STATUS。这两条链不能用相同属性名字合并为一个“玩家基础偏移”。

### 三、攻击速度：单位是间隔毫秒，值越小越快

源代码中ATTACK_SPEED用于与System.currentTimeMillis的差比较，因此在此服务端模型中是毫秒间隔，而非“每秒攻击次数”。`PlayerController.java:854–865` 的接收门槛以及 `CreatureController.java:307–317` 的攻击门槛都读取重算后的current值，两者分别保存自己的lastAttackMilis，并非同一个计时字段。

`CM_ATTACK.java:56–81` 请求负载只有目标ID(D)、攻击编号(C)、time(H)、type(C)，没有客户端声明的最终攻击力、伤害或攻速。它先通过PlayerController的时间检查，再查目标并调用attackTarget。请求中的time另外用于广播和延迟扣血，不是给服务端提供“认可的攻击间隔”。

双持算法在 `PlayerGameStats.java:165–228`：

1. 主手基础间隔全额计入；副手基础间隔先乘0.25并Math.round，然后计入。
2. 双持武器的bonus攻速修正器暂存；比较SimpleModifier的value，只选数值较小的一个。对于负数间隔缩减，较小表示更强。这里不是比较两个武器的最终攻击频率。
3. 其他符合路径的修正器继续按优先级应用；百分比bonus参考当时的base。
4. `CreatureGameStats.java:247–278` 先把攻击间隔保底为600；`PlayerGameStats.java:314–318` 再限制负bonus最多缩减基础间隔的一半。

对正的常规基础间隔B，最终下限可写为 `max(600, ceil(B/2))`；完整结果还取决于原始重算值。Java的Math.round(-700.5f)为-700，所以B=1401时半间隔下限是701，不能向下写700。没有在此路径发现“减速后的最大间隔上限”。

| 示例，假设只有列出的武器加成 | 基础间隔B | 未限幅结果 | 最终间隔 |
|---|---:|---:|---:|
| 单手1400，百分比修正-19 | 1400 | 1134 | 1134毫秒 |
| 主手1400、副手1200；武器修正-19和-17 | 1700 | 1377 | 1377毫秒，取-19 |
| 基础2000，百分比修正-70 | 2000 | 600 | 1000毫秒，半间隔限制生效 |
| 基础1401，百分比修正-70 | 1401 | 420 | 701毫秒 |
| 基础1000，百分比修正-70 | 1000 | 300 | 600毫秒，600保底生效 |

对照当前客户端：状态块+68的uint16位于Game.dll **RVA D71BE0**；`0x6A15E` 读它，加角色组件+1C88，再与受保护函数0x1244AE3返回的计时候选比较；`0x6A350` 更新组件时间戳。客户端此分支在now≤sum时退出，服务端在elapsed<interval时退出，等号行为也没有强行写成相同。当前客户端保护计时函数、整数回绕处理和其他攻击路径尚未全部解析。

服务端状态包相同前段位置明确命名ATTACK_SPEED；HP、MP、射程等多个字段也对齐，8,003件武器间隔相同又增加了语义对应的可信度。现在较强的解释是：**模板基础值、属性重算值、收到的缓存、上次动作时间、动作持续时间共同构成攻速行为**。目前没有证据支持“最终攻速必然只藏在一个加密数值中”；也不能因找到缓存就宣布保护表示已经全部解开。

### 四、移动速度、射程和瞬移：数值产生与位置生效分开看

此源码的玩家SPEED先保底600再封顶12000，FLY_SPEED先保底600再封顶16000。`SM_EMOTION.java:82–95、285–290` 按是否飞行选speed，再除1000f发float，同时特定情绪类型带基础/当前攻击间隔。对应的运行/飞行速度范围为0.6–12、0.6–16个坐标单位/秒；其米制解释沿用源码语义，当前客户端最终移速字段仍待追消费链，不能把这两个上限直接写到本机客户端偏移表里。

技能首目标射程在 `FirstTargetRangeProperty.java:52–96`：普通目标R=value，加武器范围时再加ATTACK_RANGE/1000f，随后加3.0容差；MathUtil要求同地图/实例且 `dx²+dy²+dz² < R²`，再做GeoEngine视线检查。坐标点技能分支另用distance≤value，没有同一套武器加成/3.0容差。AOE选目标的TargetRangeProperty另有1.5f容差，不是所有技能统一加3。

当前客户端 `0x19B20` 读取技能+724、+72C，以及同步状态的float D71BDC；也有组合技能距离与武器范围的行为。但本地路径中的1.0距离修正及flag语义，不等价于服务端的3.0或AOE的1.5。提示射程、客户端允许发起、服务端允许命中需要分别验证。

RandomMoveLoc的FRONT分支：按朝向计算 `(x + d*cosθ, y + d*sinθ, z+2)`，写DashParam，然后applyEffect调用World.updatePosition；该World方法写坐标、变更区域并按参数更新已知列表。BACK分支的lastSee始终为0、初始循环不执行，末尾覆盖XY为原XY，属于本提交的明确实现缺陷；初步几何意图与最终执行结果必须分列。

当前客户端提示路径 `0x28B960 → 0x28C468 → 0x28A420` 只消费reserved1/2的距离表达式；reserved3=1/2与五条服务端FRONT/BACK对应，是方向候选的资源证据，仍不是当前客户端执行方向的反汇编证据。

CM_MOVE读取客户端位置/方向，调用World.updatePosition并广播SM_MOVE，另有滑翔、坠落等处理。这解释了普通移动、技能位移和服务端通知是不同入口。此老模拟器的几何校验覆盖不能作为当前线上服务器的校验能力证明；视频里看见位移也不足以区分技能、位置插值、不同步或后台认可。本节没有生成移动修改或发包方案。

### 五、PVP伤害：已找到实际消费端，不能把所有比例合成一个乘数

以下R表示Java Math.round(float)，T表示向零截断；保留各步取整。说明的是这份源码的对应分支，不是未经验证的经典服最终公式。

**物理普通攻击，玩家、有武器：**

```text
W = 在 MAIN_MIN_DAMAGES..MAIN_MAX_DAMAGES 间抽整数（含两端）
D0 = R(W * POWER * 0.01f) + MAIN_HAND_PHYSICAL_ATTACK的bonus
     + skillDamages + bonusDamages [+ 当前路径的主手力量碎片加值]
D1 = max(1, D0 - R(目标PHYSICAL_DEFENSE * 0.10f))
```

入口为StatFunctions.java:276–363；普通攻击传skillDamages=bonusDamages=0。有正skillDamages的技能会比较两手武器均值，可能取副手的min/max；比较本身用整数除法。徒手和召唤物/NPC是独立分支，不能套这条。

AttackUtil.java:56–129后续顺序：判闪避/招架/盾防 → 相应减伤 → 独立判暴击与武器暴击倍率 → R(观察者物理倍率) → adjustDamages → 未命中清零/非未命中至少1 → 生成多段 → 护盾检查。盾防为 `D - trunc0(D*DAMAGE_REDUCE/100)`，因为源码整数相除后才调用Math.round；招架为T(D×0.6)，不能把这两步统一成四舍五入。

武器暴击倍率：匕首2.3，单手剑2.2，钉锤2.0，大剑/枪戟1.8，法杖/弓1.7，其余分支1.5；先R(D×倍率)，再R(D−D×PHYSICAL_CRITICAL_DAMAGE_REDUCE/1000f)。普通物理攻击的splitDamage并不是把总伤害拆分：首段D，后续每段R(D×0.1f)，因此N段未被护盾调整前合计为 `D+(N−1)*R(D*0.1f)`。多段包也不代表神石逐段抽签。

**技能专用PVP倍率在更早的阶段：**

DamageEffect.java:75–106先生成技能值，包括value+delta×技能等级以及value2/delta2的武器均值修正。只有目标Player且pvp_damage≠0时，将这个技能值乘pvp_damage/100f并R，然后把它交给物理或魔法伤害函数。bonusDamage是另一参数，在这一步不一同乘倍率。字段缺省0表示跳过该修正，不是“PVP零伤害”。DelayDamageEffect也有同样的早期消费。

这回答了倍率120/130怎么用：它们在已追到的这两类效果中调节**技能项**，不是把武器基础、bonusDamage和结算后的所有伤害统一提高20%/30%。其他效果家族仍需看自己的消费端。

**共同PVP修正 adjustDamages，AttackUtil.java:651–713：**

```text
D2 = R(D * 0.60f)
a = 攻击者PVP_ATTACK_RATIO * 0.001f
b = 目标PVP_DEFEND_RATIO * 0.001f
D3 = R(D2 * (1 + a - b))
```

适用攻击者Summon/Player/NpcWithCreator、目标Player/Summon的该分支。注释说50%，实际代码60%；装备PVP攻防比例是在同一括号里相减，**不是(1+a)*(1-b)**。这一步函数内未见该比例的单独上下限，后续攻击分支对非未命中结果设至少1；不能把它解释为全局没有限制。

若双方actingCreature是Player且种族不同，还按Influence比例选择1.2、1.15或1.1，然后用int复合赋值向零截断；满足后面的自定义等级配置时再执行等级修正。配置 `gameserver.dmgreduction.lvldiffpvp` 注解默认false。其diff=3..14的代码是 `baseDamages -= diff*0.04f`，并非乘(1−diff×4%)：例如正伤害660减0.12f后截断为659。diff≥15才乘0.4并截断。此处很可能存在作者意图与实现差异，但本节只把实际行为当事实。

例如进入共同PVP修正前D=1000，a=0.2、b=0.1，则先600，再660；若错误地相乘，会算648。种族祝福、技能前段倍率、暴击、盾防、观察者及护盾还会改变这个例子，因此不能用660代表所有对战情景。

**魔法伤害需区分普通魔法攻击与技能：**

- 普通魔法攻击：R(随机武器值×KNOWLEDGE×0.01f)+MAGICAL_ATTACK bonus，再R(D×(1−元素防御/1000f))，至少1；此函数不使用BOOST_MAGICAL_SKILL。
- 魔法技能：StatFunctions.java:480–505计算 `R(baseDamages*(K/100f + BOOST_MAGICAL_SKILL/1000f)) + bonusDamages`，再乘元素防御并R、至少1。实际被调用形参dot=true时K=100，false才读取KNOWLEDGE。调用方将变量命名applyKnowledge，但不能按这个名字反推布尔语义；DamageEffect默认调用传true。
- 魔法暴击先执行int的 `D *= 1.5f`（向零截断），再R暴击减伤；随后PVP/等级adjust，再R观察者魔法倍率，与物理普通攻击的顺序不同。
- 普通魔法攻击的calculateMagicalStatus竟调用**物理暴击率**函数；魔法技能用calculateMagicalCriticalRate。这是此提交的一处可见行为差异，不能套用“魔法均由魔法暴击决定”的简化结论。

玩家魔增在重算时上限2600；元素抗性下限-90，但伤害函数与重算函数不是同一个边界。魔法抵抗值MAGICAL_RESIST用于命中概率，元素抗性用于伤害倍率，二者不是一个“魔防”。

**真正扣血在服务端：** CreatureController累加AttackResult并广播SM_ATTACK；time=0立即调用目标onAttack，否则调度延后；onAttack经过施法打断、观察者、仇恨和伤害通知，最后调用LifeStats.reduceHp。DamageEffect则把计算值放reserved1，applyEffect再调用onAttack。护盾/反射等也会修改AttackResult，完整公式必须带分支，不能只截到adjustDamages就声称是最终扣血。

对照当前客户端：此前还原的物理/魔法公式位于提示格式化函数，末端是CVTTSS2SI向零截断；服务端主要使用Math.round，且多处显式/复合赋值截断。提示公式中POWER变化的系数也不能与服务端随机基础攻击的POWER×0.01直接等同。客户端收到的S_ATTACK会建立动作队列，收到攻击结果会选择“距离过远/过近/障碍”等提示，它们支持“表现/接收”职责，尚未证明本机还完整执行了上述PVP扣血公式。

### 六、命中、暴击与防御阈值：先分属性差，再分抽签与顺序

以下省略强制状态覆盖，整数除法均向零截断。双持时部分命中/暴击值先取两手整数均值，即使外面写Math.round，也不能恢复被整数除法截掉的0.5。

| 源码分支 | 计算出的判定阈值 | 取值限制 |
|---|---|---|
| 闪避 | (目标EVASION−攻击命中−技能accMod)/10 | ≤0返回1，上限30 |
| 招架 | (目标PARRY−攻击命中)/10 | ≤0返回1，上限40；普攻需目标持武器 |
| 盾防 | (目标BLOCK−攻击命中)/10 | ≤0返回1，上限50；普攻需目标持盾 |
| 魔法抵抗 | (MAGICAL_RESIST−MAGICAL_ACCURACY−accMod)/10；目标高超过2级再加(级差−2)×10 | 下限0，上限95 |
| 物理暴击净值C | R(双持均值或主手暴击×criticalProb−目标物理暴击抵抗) | 再进入下述分段 |
| 魔法暴击净值C | R(魔法暴击×criticalProb−目标魔法暴击抵抗) | 同样分段 |

暴击阈值r(C)：C≤440为C×0.1f；440<C≤600为44+(C−440)×0.05f；C>600为52+(C−600)×0.02f；r最低1。这一函数没写最高概率限制，但抽签结果本身有限。

关键是消费者多用 `Rnd.get(0,100) < r`，随机集合为0..100，共101个整数。整数阈值r对应r/101；非整数对应满足条件的整数个数/101，等效为裁剪后的ceil(r)/101。不是把r除100，也不是每点属性都平滑增加概率。源码中的float32舍入会影响恰好靠近整数的阈值，应保留计算顺序。

| 净暴击C | 阈值r约值 | 通过抽签的整数个数 | 概率（均匀假设） |
|---:|---:|---:|---:|
| 400 | 40 | 40/101 | 39.6040% |
| 440 | 44 | 44/101 | 43.5644% |
| 441 | 44.05 | 45/101 | 44.5545% |
| 450 | 44.5 | 45/101 | 44.5545% |
| 600 | 52 | 52/101 | 51.4851% |
| 601 | 52.02 | 53/101 | 52.4752% |
| 700 | 54 | 54/101 | 53.4653% |

440/600是**扣除抵抗、乘criticalProb后的净值拐点**，不是任何目标都通用的面板“毕业值”。小数阈值与整数抽签使同一小区间可能没有实际概率增益；不同目标的抵抗又会移动区间。这是这份模型对配装有用的地方。

普通物理攻击先独立抽闪避，未闪避再抽招架，未招架再抽盾防。设各自抽签概率d/p/b，则实际闪避d、招架(1−d)p、盾防(1−d)(1−p)b；不能把三个阈值直接相加。三个阈值都封顶、目标持武器/盾、无强制状态时，实际约为29.7030%闪避、27.8404%招架、21.0181%盾防、21.4385%正常命中状态；暴击随后可与招架/盾防组合。盾防发生率与盾防减伤百分比是两个不同属性。

物理技能在AttackUtil的状态函数里没有闪避检查，不代表技能不能闪避：EffectTemplate.java:311–329在共用成功效果路径另抽闪避/魔抗，noresist可跳过；异常抵抗、条件效果、前置效果也会阻止执行。因此技能命中概率不能仅从calculateSkillPhysicalStatus推导。

源码返回阈值100的“总是闪避/暴击”路径如果仍经过0..100的严格小于抽签，只能100/101；不要把注释或观察者名称当作100%必然成功。其他直接跳过抽签的路径需另审。

### 七、神石：第二参数在这份源码中参与一次随机阈值，不能只读提示百分比

`GodStone.java:76–110` 装备时安装ATTACK观察者，卸下移除。每次attack回调：

```text
p = probability，L = probabilityleft（Java缺省0）
T = Rnd.get(p-L, p)                      # 两端都含
若是双持副手神石：T = trunc0(T * 0.5)
U = Rnd.get(0,1000)                      # 1001种整数结果
若 T > U：尝试神石技能 → canUseSkill/目标条件 → Effect初始化/应用
```

若0≤L≤p≤1000且整数均匀，主手通过随机分支的概率为 `(p−L/2)/1001`。副手必须对每个T取floor(T/2)后求均值再除1001，奇数阈值使它不一定恰好是主手的一半。两层随机数和后续效果抵抗都在源码的服务端路径，客户端对应参数是资源/提示数据，未证明它能决定结果。

例如物品168000034两边都有p=60、L=30。此模拟器T在30..60抽，平均45，随机分支概率45/1001≈4.4955%；只用p/10会显示6%。副手该区间的平均截断阈值为690/31，随机分支约2.2236%。物品168000028两边p=40且第二参数缺省，在此模拟器随机分支是40/1001≈3.9960%。这些只说明源码实现，不证明经典服正式概率；资源是否正式可用也另查。

普通攻击通知神石观察者在CreatureController.java:362–373：闪避/抵抗跳过，其余状态通知。多段攻击先累加结果，再一次notifyAttackObservers；并非splitDamage的每一段都抽一遍。DamageEffect/DelayDamageEffect也有通知入口，能否触发还取决于成功效果链和技能限制。本轮没有把所有技能、持续伤害及反射归为相同触发频率。

即使随机分支通过，仍可能因canUseSkill、当前目标或Effect抵抗未产生可见效果；弹出发动消息也在部分后续检查之前。因而战斗日志“最终看见的神石效果次数/攻击次数”不等同于单独的T>U概率。

### 八、强化：服务端判定、持久状态写回与客户端概率提示已明确分开

`EnchantService.enchantItem:119–280` 的成功阈值：

```text
Q = COMMON/JUNK:0；RARE:5；LEGEND/MYTHIC:10；EPIC/UNIQUE:15
S = 50 + 5*max(石等级−装备等级−Q, 0) + 辅助剂加值
S = min(S,95)
成功 = Rnd.get(0,100) < S
```

前置条件包括目标可强化、石等级不低于装备等级；此方法先消耗强化石，再按条件消耗辅助剂。辅助剂默认加10，三个配置注解默认10/15/20；真正启动时配置可覆盖。目标强化等级超过10会增加辅助剂消耗，但**这个方法的成功率没有因+11..+15单独减半**。

如果成功：UNIQUE/EPIC最高15，其他最高10；失败：当前>10回到10，当前1..10减1，0不再减。随后必要时卸下旧属性修正、setEnchantLevel、重新应用属性，发送SM_UPDATE_ITEM，并标记装备/背包UPDATE_REQUIRED，再发送成功/失败消息。持久状态标记已确认，数据库最终落盘调度不是本节已完整审计的范围。

| S阈值 | 真实通过整数个数 | 模型概率（均匀假设） |
|---:|---:|---:|
| 50 | 50/101 | 49.5050% |
| 60 | 60/101 | 59.4059% |
| 80 | 80/101 | 79.2079% |
| 95，封顶 | 95/101 | 94.0594% |

以品质Q=15、石比装备高20级为例：无辅助剂S=75，加默认普通辅助剂15为S=90；高25级时基础达到100后封顶95。以上是输入分层示例，不是建议为核验额外购买或消耗材料。

当前客户端 `0x316610` 已还原的UI公式使用品质系数60/40/30/20/15/10；+1..+10基础封顶800，+11..+20先除2再封顶500，辅助剂后总值封顶1000，显示乘0.1。它与本服务端的品质减项、封顶95和不区分高阶基础概率的实现明显不同。对比揭示“提示概率≠源码判定概率”，不能选一个更好看的数当线上真实概率。

### 九、这轮结论对PVP和强化学习的具体帮助

1. 攻速配装要看主副手基础间隔、武器加成选择、其他修正器和下限。达到某条间隔下限后，同路径再堆加速没有继续减少间隔的收益；它仍可能改变其他动作或技能，需逐条看消费端。
2. 命中能同时改变闪避、招架、盾防差值，但这些状态依序排斥；盾防概率与盾防减伤分别评估。暴击要减目标抵抗后看440/600拐点与整数抽签，不使用固定面板阈值。
3. PVP倍率要分技能项、装备攻防项、种族祝福、等级配置、暴击及护盾。源码可以建立明确模型和装备比较假设，正常玩法的同装备/技能/目标/阶段日志才能核对当前版本。
4. 神石要记录主副手、第二参数、实际通知次数与效果抵抗；强化要记录品质、石装等级差、辅助剂配置与强化阶段。一次成功或失败没有证明概率的能力；有限样本只能给分层估计/置信区间。

已完成的主要源码链不再是待定。仍待追的是当前客户端RandomMoveLoc方向执行、最终移速同步消费者、保护计时函数、当前版本PVP参数消费，以及源码尚未逐家族审计的护盾/吸收/反射/治疗/异常抵抗/召唤物路径。后续可沿这些具体入口继续，不必为了本节结论附加正在游玩的客户端。
